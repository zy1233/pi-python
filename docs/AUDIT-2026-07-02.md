## 总体结论

纯 mock 路径（现有测试覆盖的部分）语义基本正确；**真实 LangChain 路径与若干移植细节存在 10+ 个
实质性缺陷**，其中 4 个属于"上线即坏"级别（P0）。所有关键结论均经运行时实测或依赖源码核对证实。

## 一、设计与实现偏差

### D1. "并行"工具执行实际是串行的

- [x] **已修复（2026-07-02）** ·（严重 · 实测）
- 位置：`pi_agent_core/agent_loop.py` `_execute_tool_calls_parallel`
- 问题：DESIGN.md §3 承诺 `tool_execution_end` 按**完成顺序**发射，pi 原版用 `Promise.all` 并发。
  Python 版把闭包存入列表后逐个 `await`，完全串行。实测 2×300ms 工具耗时 0.61s（并行应 ~0.3s）。
- 影响：吞吐减半起步；"完成顺序发射"语义不存在。
- 修复：闭包统一 `asyncio.create_task` 启动后按源顺序 await——并发执行、`tool_execution_end`
  按完成顺序、`toolResult` 消息仍按源顺序持久化（与 pi 语义一致）。

### D2. `Agent(prepare_next_turn=...)` 必然崩溃

- [x] **已修复（2026-07-02）** ·（严重 · 实测）
- 位置：`pi_agent_core/agent.py` `_create_loop_config` 内 `prepare()` 包装器
- 问题：包装器定义为无参函数，而 `agent_loop` 调用 `config.prepare_next_turn(next_ctx)` 传入
  1 个位置参数 → `TypeError: prepare() takes 0 positional arguments but 1 was given` → 整个
  run 以 error 收场，用户钩子从未被调用。TS 版包装器签名为 `async (context) => ...`。
- 修复：包装器改为接收 `next_ctx` 参数（当前忽略，与 TS 无 context 版本钩子对齐），并补回归测试。

### D3. `prepare_next_turn` 返回的 `thinking_level` 被忽略；config 被原地修改

- [x] **已修复（2026-07-02）** ·（中 · 代码审查）
- 位置：`pi_agent_core/agent_loop.py` `_run_loop`（快照应用处）
- 问题：TS 应用快照时更新 `config.reasoning`；Python 只应用 `context`/`model`，
  `AgentLoopTurnUpdate.thinking_level` 形同虚设。且 `config.model = snapshot.model` 原地改写
  调用方传入的 config（TS 创建副本），直接使用 `run_agent_loop` 的用户会被跨 run 污染。
- 修复：快照的 `model`/`thinking_level` 通过 `dataclasses.replace` 应用到 config **副本**，
  调用方对象不再被污染。回归测试验证第二轮 `options.reasoning` 生效且原 config 不变。

### D4. `after_tool_call` 同时返回 `content` + `details` 时 `details` 丢失

- [x] **已修复（2026-07-02）** ·（中 · 实测）
- 位置：`pi_agent_core/agent_loop.py` `_finalize_executed_tool_call`
- 问题：TS 是三路独立合并（`content ?? old / details ?? old / terminate ?? old`），Python 写成
  `if content... elif details...`。实测同时返回两者时 details 保持旧值。
- 修复：改为一次性三路独立合并（每个字段独立回退到执行结果），删除冗余重建。

### D5. reasoning 注入违反设计"仅 o 系列"的约束

- [x] **已修复（2026-07-02）** ·（中 · 代码审查）
- 位置：`pi_agent_core/adapters/langchain_stream.py` `_apply_reasoning_params`
- 问题：Phase 2 设计明确 OpenAI `reasoning_effort` 仅 o 系列模型，实现只判断 provider 不判断
  模型系列，对 `gpt-4o` 等开 `thinking_level` 会 API 400。
- 修复：不再按模型名硬编码（会随新模型过时），改用 `Model.reasoning` 能力位作为注入门槛：
  `model.reasoning=True` 且 `thinking_level != off` 才注入。能力声明由用户在 Model 上给出，
  与 `transform_messages` 的 thinking 剥除逻辑共用同一开关（见 B7 联动）。设计文档同步修正。

### D6. 流事件粒度缩水，thinking 无流式更新

- [x] **已修复（2026-07-02，thinking_delta 部分）** ·（低 · 代码审查）
- 位置：`pi_agent_core/types.py`（事件类型）、`langchain_stream.py`（thinking 分支不 push 事件）
- 问题：pi 有 9 种 AssistantMessageEvent（含 `thinking_start/delta/end`）；Python 只有 5 种，
  且 thinking 增量只更新内部状态不发事件，UI 无法流式渲染思考过程。
- 修复：新增 `ThinkingDeltaEvent`（`type="thinking_delta"`），thinking 增量实时发射并透传为
  `message_update`，UI 可流式渲染思考过程。`text_start/end`、`thinking_start/end` 等
  start/end 粒度事件属增强项，列入第三部分后续讨论。

## 二、实现 Bug

### B1. Anthropic 绑定工具/开启 thinking 后，助手文本全部丢失

- [x] **已修复（2026-07-02）** ·（致命 · 实测）
- 位置：`pi_agent_core/adapters/langchain_stream.py` `_produce` chunk 循环
- 问题：langchain-anthropic 仅在无 tools、无 thinking 时才把 chunk.content 压成字符串
  （源码 `coerce_content_to_string`）。Agent 场景必绑工具 → content 是
  `[{"type": "text", "text": ..., "index": 0}]` 列表形态，而适配器只认 `isinstance(content, str)`
  → text_delta 不发射、最终 AssistantMessage 无 text 块。实测文本完全蒸发。
- 修复：新增 `_extract_text_delta()`，str 与 list 两种形态统一提取文本（list 形态同时兼容
  OpenAI responses API 的块结构）。

### B2. usage 提取对两家 provider 都不可靠

- [x] **已修复（2026-07-02）** ·（严重 · 依赖源码核对）
- 位置：`pi_agent_core/adapters/langchain_stream.py` `_extract_usage`；Phase 2 设计文档映射表
- 问题：
  1. Anthropic 分支读 `meta["cache_read_input_tokens"]`——LangChain 标准化 `usage_metadata`
     无此字段（实际在 `input_token_details.cache_read/cache_creation`，已核对
     langchain-anthropic `_create_usage_metadata` 源码）→ cache 恒 0。
     **设计文档映射表本身错误**（抄了 Anthropic 原始 API 字段名），代码忠实实现了错误设计。
  2. 依赖"最后一个 chunk"脆弱：旧版 langchain-openai `stream_usage` 默认 False（1.x 才默认
     True），`pyproject.toml` 仅约束 `>=0.2.0` → 低版本 usage 全 0。
- 修复：`_extract_usage` 重构为 `_merge_usage_meta`（逐 chunk 逐字段累加，对齐 LangChain
  `add_usage` 语义，兼容分片上报）+ `_usage_from_meta`（两家统一读标准化的
  `input_token_details.cache_read/cache_creation` 与 `output_token_details.reasoning`，
  删除 provider 分支）；ChatOpenAI 显式 `stream_usage=True`；Phase 2 设计文档映射表已修正。

### B3. `tool_execution_update` 不实时，同步调用则静默丢失

- [x] **已修复（2026-07-02）** ·（严重 · 实测）
- 位置：`pi_agent_core/agent_loop.py` `_execute_prepared_tool_call`
- 问题：`on_update` 实现为 `async def`，函数体只把 emit 协程 append 进列表，工具执行完才统一
  await。实测：① 工具 await on_update → 进度事件在工具结束时才发出；② 工具按声明类型
  `AgentToolUpdateCallback = Callable[[AgentToolResult], None]`（同步签名）直接调用 →
  更新完全丢失 + RuntimeWarning。TS 版 emit 是立即启动的 Promise。
- 修复：`on_update` 改为同步函数，内部 `asyncio.ensure_future(_emit(...))` 立即调度（对齐 TS
  立即启动的 Promise），执行结束后统一 await 收尾；返回该 task 使旧式 `await on_update(...)`
  用法继续可用；执行结束后置 `accepting_updates=False` 拒绝迟到更新（同 TS）。回归测试
  验证事件在工具运行期间送达。

### B4. abort 之后循环仍会发起下一轮 LLM 请求

- [x] **已修复（2026-07-02）** ·（严重 · 实测）
- 位置：`agent.py` `_AbortSignal`、`agent_loop.py` `_run_loop`、`langchain_stream.py`
- 问题：① `_AbortSignal` 只是布尔位，无法取消进行中的 HTTP 请求/工具（pi 的 AbortSignal 挂到
  fetch）；② `langchain_stream` 只在收到 chunk 后检查 abort，首 token 前无法中止；③ `_run_loop`
  工具批次结束后、下一轮前不检查 signal。实测 abort 后 `turn_start` 计数 = 2。
- 修复：`_AbortSignal` 增加 `asyncio.Event` 与公开 `wait_aborted()`；`langchain_stream`
  ① 发起请求前检查已中止（下一轮立即产出 aborted 消息收尾——与 pi 依赖 streamFn 响应
  abort 的架构一致，`_run_loop` 无需额外检查）；② 消费循环与 `wait_aborted()` 竞争等待，
  首 token 前即可中止，且通过 `Task.cancel` 真正取消 HTTP 请求；③ 保留逐 chunk 轮询兼容
  仅有 `.aborted` 布尔位的自定义 signal。回归测试验证挂起首 token 时 abort 快速返回
  且请求任务被取消。工具侧 signal 继续透传由工具自愿响应（同 pi，不强杀）。

### B5. `resolve_chat_model` 第三方 provider fallback 分支从未可用

- [x] **已修复（2026-07-02）** ·（严重 · 逻辑实锤）
- 位置：`pi_agent_core/adapters/langchain_stream.py` `resolve_chat_model`
- 问题：`init_chat_model(model.model_id, ..., **kwargs)` 而 kwargs 含 `"model"` key →
  `TypeError: got multiple values for argument`；且 `langchain` 包不在依赖中 → `ImportError`；
  两者均被 `except Exception` 吞掉变成误导性的 `ValueError: Unsupported provider`。
- 修复：ImportError 单独捕获并给出安装指引；调用前从 kwargs 剔除 `model` key；不再吞掉
  init_chat_model 的真实报错。

### B6. reasoning 参数经 `model_kwargs` 注入是错误通道

- [x] **已修复（2026-07-02）** ·（中 · 实测）
- 位置：`pi_agent_core/adapters/langchain_stream.py` `_apply_reasoning_params`
- 问题：`reasoning_effort` / `thinking` 都是 ChatOpenAI / ChatAnthropic 的显式构造参数。实测
  当前版本触发 UserWarning 后被 langchain 搬回顶层（侥幸可用）；旧版 langchain-core 走
  `build_extra_kwargs` 直接 ValueError。另外 Anthropic thinking 要求 `max_tokens > budget_tokens`，
  代码未设置 max_tokens，在 max_output_tokens 较小的模型上 medium 以上档位必然 API 报错。
- 修复：改为顶层构造参数注入；Anthropic 自动设置 `max_tokens = budget + 8192`（用户显式传入
  时不覆盖）。注入门槛联动 `Model.reasoning` 能力位（见 D5）。

### B7. Anthropic thinking + 工具的多轮回放必然 400

- [x] **已修复（2026-07-02）** ·（中 · 代码审查 + Anthropic API 约束）
- 位置：`adapters/langchain_convert.py`、`messages.py`（ThinkingContent 无 signature 字段）
- 问题：`convert_to_langchain` 丢弃 ThinkingContent 且未保存 signature（pi 存
  `thinkingSignature`）；Anthropic 要求 thinking 开启时带 tool_use 的 assistant 消息以带签名的
  thinking 块开头 → 第二轮请求 400。连锁：thinking 开关双源不联动——`Agent.thinking_level`
  控制请求参数、`Model.reasoning`（默认 False）控制 `downgrade_thinking` 剥除 → 用户开
  thinking_level 未设 reasoning=True 时 thinking 块每轮被静默剥掉。
- 修复：① `ThinkingContent` 增加 `signature`（NotRequired）字段；`langchain_stream` 从
  Anthropic chunk 捕获 signature 并写入最终 thinking 块；② `convert_to_langchain` 回放
  thinking 块（含 signature，置于 text/tool_use 之前，无 thinking 时保持原字符串形态）；
  ③ 双源联动收敛为单一规则：**开启 thinking = `Model.reasoning=True` 且
  `thinking_level != off`**——reasoning=False 时既不注入参数也剥除历史 thinking（一致），
  reasoning=True 时注入参数且保留回放（一致），静默剥除不再发生。

## 三、对照主流 Agent Harness 的设计不足（后续讨论，暂不实施）

参照 pi 本体、LangGraph、OpenAI Agents SDK、Claude Agent SDK、DeepAgents：

| # | 缺失能力 | 主流对标 | 优化方向 |
|---|---------|---------|---------|
| 1 | LLM 重试/退避 | pi `maxRetryDelayMs`；各家标配 | `langchain_stream` 内指数退避（尊重 Retry-After）或透传 langchain `max_retries` |
| 2 | 失控保护 | OpenAI SDK `max_turns`；LangGraph `recursion_limit` | `AgentLoopConfig` 加 `max_turns`、`tool_timeout` |
| 3 | 持久化/断点恢复 | LangGraph checkpointer；Claude SDK session | Phase 3 Session JSONL 对齐 checkpoint 语义：每 turn 原子落盘 + `continue_()` 恢复 |
| 4 | 上下文预算管理 | Claude Code compaction | 基于 `usage.totalTokens` 阈值触发的内置 `transform_context` 压缩；`Model.context_window` 目前无人消费 |
| 5 | Guardrails 钩子面 | OpenAI SDK input/output/tool 三类 | 补 `before_llm_call` / `after_llm_call` / `on_agent_end` |
| 6 | 可观测性 | pi `onPayload/onResponse`；LangSmith/OTel | 恢复 on_payload/on_response；事件带 run_id/turn_id；顶层异常记日志 |
| 7 | 结构化输出 | 各家标配 | `StreamOptions.response_schema` → langchain `with_structured_output` |
| 8 | 工具生态接入 | LangChain `@tool`/`BaseTool` 生态 | 提供 `from_langchain_tool()` 适配器 |
| 9 | 多模态工具结果 | pi 支持 tool result 图片 | convert 层转换 ImageContent（Anthropic 原生；OpenAI 需 user 消息 fallback） |
| 10 | 取消语义 | asyncio 结构化并发惯例 | signal 持 `asyncio.Event`，abort 即 `Task.cancel`（呼应 B4） |

架构备注：`transform_messages` 内置于 `langchain_stream` 每轮对全量历史 O(n) 复制转换，长对话
下重复付费，建议移到 `convert_to_llm` 边界做增量缓存。事件协议（六段式生命周期 + steering/
follow-up 队列）是本库差异化价值，应保留。
