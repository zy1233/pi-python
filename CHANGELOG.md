## [Unreleased]

### Added

- **A console script with the name of the package (`pi-agent-cli`)**: `pi-agent-cli-lc` starts the same function as `pi-agent-cli`, which stays. `uvx <package>` runs the executable that has the name of the package, and it stops with an error when the package has none. The package had only `pi-agent-cli`, so `uvx pi-agent-cli-lc==0.6.0` printed "An executable named `pi-agent-cli-lc` is not provided by package `pi-agent-cli-lc`". The ACP registry starts a PyPI agent only in this form (`uvx <package> <args>`; it has no `--from`), so a registry entry needs this script. It reaches PyPI with the next release. `uvx --from pi-agent-cli-lc pi-agent-cli` works with every release. Test: `packages/pi-agent-cli/tests/test_console_scripts.py`.
- **The README tells how to start the agent in Zed as a custom agent (docs)**: the section "In Zed (custom agent)" has the `agent_servers` entry (`uvx --from pi-agent-cli-lc`), the place of the model and key settings, and the entry for a checkout. The command of the entry was run with the published 0.6.0 package: the agent answered `initialize` in an empty home. It was not run inside Zed.

### Changed

- **The release workflow builds the Linux binary on `ubuntu-24.04`, not on `ubuntu-latest` (CI)**: GitHub moves the label `ubuntu-latest` to Ubuntu 26. A binary that is built there can need a newer glibc than the 2.39 of Ubuntu 24.04, and then a machine with Ubuntu 24.04 could not start it. The job `build-tui` in `release.yml` now names the image, as `TUI CI` does (ADR6) and as `build-tui-macos-arm` does with `macos-14`. Nothing changes for the files of a release: the build of `v0.6.0` ran on `ubuntu-24.04` already. The other jobs of `release.yml` (tests, Python packages, publishing) still use `ubuntu-latest`; they ship no binary.
- **The documentation says that the Linux binary needs glibc 2.39 or newer (docs)**: `docs/TUI-AND-CODE-AGENT.md`, Option A. The binary of `v0.6.0` has `GLIBC_2.39` as its highest versioned symbol, so a system with an older glibc cannot start it (Ubuntu 22.04 has 2.35). Option B (build from source) works there.
- **The workflows use the Node 24 versions of three GitHub Actions (CI)**: `actions/upload-artifact` v4 to v6, `actions/download-artifact` v4 to v7, and `actions/cache` v4 to v5. GitHub removed Node 20 from its runners on 2026-09-23. It runs the old versions on Node 24 and prints a warning. The new versions change only the runtime; the inputs that the workflows use are the same. `arduino/setup-protoc@v3` stays: it has no release for Node 24, and it works on Node 24 (the runs of 2026-10-26 passed). `download-artifact` runs only in the jobs that publish, so a dry run of `release.yml` does not test it.

### Fixed

- **The benchmark runner showed the verifier's tests to the agent (`pi-agent-cli`)**: `DockerContainerSession.setup()` copied the task's `tests/` into the container as `/tests` when the container started. The agent has a shell in that container, so it could read `test.sh`, `test.patch`, `grader.py` and `test_outputs.py`. This was so from the first version of the runner (2026-09-04). Now `setup()` copies nothing. `run_verifier()` installs `/tests` after the agent is done, and first removes any `/tests` that the agent made. DeepSWE's `task.toml` asks for this (`[verifier] environment_mode = "separate"`). **Affected results**: a scan of all 65 saved trajectories found one Terminal-Bench pass that read `/tests` (`extract-elf`, 2026-09-07), and one `--no-docker` run that read the task cache with `tests/` and `solution/` in it (`polyglot-c-py`, 2026-09-10). The first no longer counts. The report does not use the second. Numbers and method: `docs/benchmarks/FRONTIER-HARNESS-30-EVAL-REPORT.md`, section "数据有效性声明". Test: `packages/pi-agent-cli/tests/test_docker_runner_verifier_isolation.py`.
- **A DeepSWE run scored -1 when the agent had committed a file with the name of a hidden test (`pi-agent-cli`)**: the task text tells the agent to work on a new branch and to commit. DeepSWE's `grader.py` assumes that HEAD is the base commit. It resets the files that `test.patch` touches with `git checkout HEAD -- <file>`, and it deletes a file only when HEAD does not have it. A file that the agent had committed under the name of a hidden test (`tests/test_multipart_response.py` in `httpx-multipart-response-parsing`) stayed, `git apply test.patch` failed with "already exists in working directory", and the run scored -1 without any test run. The official flow is not affected: it applies the agent's diff to a fresh container. Now `setup()` records HEAD, and `run_verifier()` moves HEAD back with `git reset --mixed` before the verifier starts. Only HEAD and the index move; the files stay as the agent left them. This applies only to tasks whose `tests/` has `grader.py` and `config.json`; Terminal-Bench tasks keep their history (for `sanitize-git-repo` the new history is the answer). **Affected results**: one trial. Of the 6 trials of the 100-turn rerun (2026-10-26), `httpx-multipart-response-parsing` scored -1; a re-grade of its saved workspace with the fix gives F2P 122/122 and P2P 1272/1272. Three other trials of that rerun also had commits (`expr-try-catch-errors`, `katex-multicolumn-array-spans`, `meriyah-explicit-resource-declarations`); a re-grade with the fix gave the same counts as before. A search of all saved `verifier_output.txt` files (the 60-turn DeepSWE trials of 2026-10-16 included) finds this error in that one trial only. Test: `packages/pi-agent-cli/tests/test_docker_runner_verifier_head.py`.
- **An extension did not find its own entries with `get_custom_entries` (`pi-agent-core`, `pi-agent-harness`)**: the method returned the entries that the session had when the extensions loaded. An entry that an extension wrote with `append_entry` in the same session was not in the list. Now the list holds the entries of the session first and then the entries that were written after that, in order. An entry that the session has not written yet has an empty `id`. goal-x reads its state only at `session_start`, so it was not affected. Audit F7-02. Test: `packages/pi-agent-harness/tests/test_harness_extension_state.py`.
- **`ExtensionAPI.run_async` raises `RuntimeError` when no event loop runs (`pi-agent-core`)**: it called `asyncio.get_event_loop()`. With no running loop, Python 3.12 and 3.13 made a loop that never ran (and gave a `DeprecationWarning`), so the task never ran; Python 3.14 raises `RuntimeError`. Now the method uses `get_running_loop()` and closes the coroutine, and all Python versions raise at once. **Behavior change** for an extension that called it outside a running loop: it got a task that never ran, and now it gets the exception. No extension in this repository calls `run_async`. Audit F7-03. Test: `pi_agent_core/tests/test_extension_api_rules.py`.
- **An extension that registers a command name that cannot be used fails to load (`pi-agent-core`)**: the harness finds a command by the text between the `/` and the first white space. A name that is empty, that holds white space, or that starts with `/` could never be run, but the clients were told about it. `register_command` now raises `ValueError` for such a name, as `register_tool` does for a tool name. In `activate()` this fails the load of that extension and rolls back its other registrations; the other extensions still load. **Behavior change**: such an extension used to load. Audit F7-04. Test: `pi_agent_core/tests/test_extension_api_rules.py`.
- **A directory extension that failed to import stayed in `sys.modules` (`pi-agent-core`)**: the loader puts the module in `sys.modules` before it runs the file, as the import system does, but it did not take it out when the file raised. The name (`_pi_ext_<file name>`) is the same for the extension files of all projects, so a half-written module could be found later by that name. Now the entry is taken out, and an older module of the same name is put back. This is also so for `sys.exit()`. The failure is still in `failed`, with the same text. Audit F7-05. Test: `pi_agent_core/tests/test_extension_loading_rules.py`.
- **The harness logs a warning when an extension tool takes the name of a built-in tool (`pi-agent-harness`)**: the extension tool replaces the built-in tool. This is allowed, and it did not change. But the permission check reads the `annotations` of the tool that is in place, so an extension tool that declares itself read-only and is called `bash` is not asked about in `ask` mode, and nothing was logged. Now the harness logs one warning with the tool name and the extension name. Audit F7-06. The harness still sends no `ToolsUpdateEvent` when a tool is added after the load: nothing in the ACP layer reads that event. Test: `packages/pi-agent-harness/tests/test_harness_extension_state.py`.
- **Three notes in the Phase 7 spec are corrected (docs)**: §3.5 said that `session_start` is `before_agent_start`; it is sent once, after the extensions load (§4.3). §3.4 and the docstring of `ExecuteFn` now say that the harness calls `execute(tool_call_id, params, signal, on_update)` with four positional arguments, and that a function that takes two fails with `TypeError` when the tool is called. §14 lists the fields that go into the hash of a journal entry (`timeout_ms` is not one of them). Audit F7-07 to F7-09.

### Known issues

- **The `allowlist` egress mode of the benchmark runner does not filter (`pi-agent-cli`)**: the Terminal-Bench tasks use it. The runner passes only proxy variables to the container, and `EgressPolicy.allowed_hosts` goes into `run.json` and nowhere else. A test on 2026-10-16 reached `example.org`, `huggingface.co` and `httpbin.org` through the proxy. The official list itself has `github.com`. One agent used this to download the reference solution of its own task, so that run does not count. `--egress-mode no-network` rules this out (a task that needs `apt-get` then fails). `--no-docker` runs share the file system with the agent. Use them for smoke tests only.

## [0.6.0] - 2026-10-25

This release makes `zypi` ask the Python agent for sessions, and it adds an optional package that connects MCP servers. **Changed** says how `--continue`, `--resume` and `--session-id` work now, and that a session in which nobody typed has no file. `pi-mcp-py` (**Added**) connects the MCP servers that an editor such as Zed passes to the agent; without it, the agent still has no MCP client. **Fixed** has the Zed thread that did not open again after a restart. **Removed** lists the TUI code that read session files, and other dead code. **Known issues** says what does not work yet. **Changed** also has the new version numbers: the extension packages need the new core.

### Added

- **Tools that find tests which share process-wide state, and a helper that keeps such a test apart (TUI tests)**: `scripts/tui_envspy/` and `in_own_process`. All tests of one Rust test binary run as threads of one process, so they share the environment variables, the working directory and every `static`. The vendored tests were written for `cargo nextest` (one process per test), so their locks are partial, and a test that changes such state can break another test in some runs only. `envspy.sh` runs `cargo test` with an `LD_PRELOAD` shim over `getenv`, `setenv`, `unsetenv`, `putenv` and `chdir`, and `analyze.py` lists the tests that change a variable while another test runs, leave it changed, or read what another test has changed. `stress.sh` runs the lib tests of one package many times, each time in a random order (`--shuffle-seed`, so a failing run can be repeated) and with many test threads. It can also run a few named tests (a suspect pair, or a victim beside all tests of one module), and with `ENVSPY_TAG` it runs the tests through the spy. Linux only. 10 new `pytest` tests cover the analyzer. `crate::test_util::in_own_process(|| { … })` in `pi-pager` runs the body of a test in a child process (the same test binary, `--exact`, one test thread), and the test fails when the child fails; 57 tests use it, directly or through `with_rtl_bidi`, `with_theme_test_env` and `with_test_env`, and 2 new tests check it. The README of `scripts/tui_envspy/` has the rules for a test that changes process-wide state, and what the tools do not find. Numbers: section 3.4 of `docs/baselines/tui.md`.
- **Extensions can take over the MCP servers a client passes, tell the user something, and hold a turn back (`pi-agent-core`, `pi-agent-harness`, `pi-agent-cli`)**: the agent still has no MCP client, and it still does not read `mcp.json`. What a client passes in `mcp_servers` now goes to the harness as data: `ClientMcpServer` (`name`, `transport`, `command`, `args`, `env`, `url`, `headers`; its `repr` shows only `name` and `transport`, because the other fields can hold tokens), `AgentHarness.set_client_mcp_servers()` (before the extensions load), and `ExtensionAPI.client_mcp_servers` with `claim_client_mcp_servers(names)`. Three general entry points come with it. `ExtensionAPI.notify(text)` shows one line to the user (a `NoticeEvent`, which is an agent message in ACP; the model does not see it, the session does not save it, and the agent holds it until the client knows the session). `ExtensionAPI.register_cleanup(callback)` is the public name of what the bridge already had. `ExtensionAPI.add_turn_barrier(wait)` makes the harness await `wait` before it builds the tool list of a turn; `session/cancel`, closing the session and opening it again end that wait in the CLI. `initialize` says that the agent takes `http` and `sse` MCP servers only when the `pi-mcp` extension entry point is installed. The extension that uses these entry points is `pi-mcp-py` (next entry). Design: `docs/specs/2026-10-23-mcp-extension-design.md`.
- **`pi-mcp-py`: an optional extension that connects the MCP servers an ACP client passes (new package `packages/pi-mcp`, version 0.1.0)**: an editor such as Zed passes its MCP servers in `session/new`. With this package installed, the agent connects them (stdio, Streamable HTTP and SSE) and gives their tools to the model. The core, the harness and the CLI still have no MCP client, and the agent still reads no `mcp.json`; the extension takes the servers from `pi.client_mcp_servers` and claims them, so the notice "its tools are not available" does not appear. Without the package, nothing changes. **Tools**: each tool is named `mcp__<server>__<tool>` (letters, digits, `_` and `-`; at most 64 characters, cut with a hash; a repeated name gets `_2`, `_3`). The prefix is needed: a tool of an extension that has the name of a built-in tool replaces it, and an MCP tool named `bash` would take over `bash`. The permission mode `ask` asks about every MCP tool call unless the server declares the tool harmless (`readOnlyHint`, or neither destructive nor open-world), as for all tools. A result is text; text over 50 KB is cut with a note, a result with only `structuredContent` is sent as JSON text, and an MCP error result becomes an error tool result. **One task for each server**: the MCP SDK uses `anyio` cancel scopes, which must end in the task that began them. `session_start` starts the servers and returns at once; a turn waits at most 10 s for servers that are still starting (`session/cancel` ends the wait) and then goes on without them. A server that is slower sends one notice, and its tools join in a later turn. **Limits** (environment variables): `PI_MCP_STARTUP_TIMEOUT` (60 s) and `PI_MCP_CALL_TIMEOUT` (120 s); a call also ends when the user cancels the turn. **When a server stops**: the user gets one notice for each server and kind of event (did not start, stopped, cannot reconnect), and a good start gets none, so a thread without MCP trouble stays blank. The next tool call connects the server again, at most 3 times in a row (a call that gets an answer starts the count again). A call that was already sent when the server died is not repeated, because the server may have run it. `/mcp` lists the servers (name, transport, state, number of tools), and `/mcp reconnect <name>` connects one again with no limit. **Secrets**: `env`, `headers`, `args` and `url` hold tokens. Notices, `/mcp`, errors and logs show only the server name, the name of the executable, or the host; the values of `env`, the values of `headers` and the URL are masked in error text. **Environment of a stdio server**: the default list of the MCP SDK, the proxy, certificate, locale and time zone variables, and the `env` of the client. `${VAR}` is not expanded (`langchain-mcp-adapters` would expand it from the environment of the agent, which has the LLM key, so the extension starts stdio servers itself), and the keys of the LLM provider are not passed. stderr of a server goes to `<home>/logs/mcp/<name>.log`, not to the stderr of the agent, where a full pipe would stop it. **Servers on this machine** are reached without the proxy of the system: `httpx` reads the proxy settings of Windows and does not skip loopback addresses. **End**: when the session closes, each server gets its stdin closed first, and then its process tree is stopped; a test checks that no process stays, on Windows and on Linux. **Not supported**: OAuth (it works only if the editor passes a token in `headers`; not verified), MCP resources, prompts, sampling and elicitation, a server shared by two sessions (each session starts its own), and a configuration file. A legacy SSE server whose POST fails ends a call only with the call timeout (the SDK hides the error). **Limits of the package**: it needs `pi-agent-core-lc` 0.6.0 or later; an older core makes it log a warning and do nothing. The `Release` workflow installs the package for its pre-release tests and builds it with the other packages, so the upload to PyPI has it (`pip install pi-mcp-py`). Tests: 192 in `packages/pi-mcp/tests` with real child processes (stdio, HTTP, SSE), the real `AgentHarness`, and the real `PiAcpAgent` over ACP, run on Windows and WSL. Design: `docs/specs/2026-10-23-mcp-extension-design.md`.

### Changed

- **`zypi --continue`, `--resume` and `--session-id` ask the agent which session is meant (TUI)**: `zypi` used to look for the session in the session files of the old Rust agent. The Python agent writes another layout, so `--resume <title>` found no session, an unknown id failed only after the UI had started, a used `--session-id` left the UI open with `Session creation failed: Invalid params`, and `--continue` took the session that was created last (the first of the **Known issues** of 0.5.0). Now `zypi` starts the agent first and then asks it over ACP, with `session/list` (page after page) and `session/load`. It reads no session file for this. A session that does not exist ends the run before the event loop starts: the terminal is restored, the agent is stopped, the message is printed, and the exit status is 1. **Behaviour changes**: `--continue` and `--resume` without a value take the session of this directory with the latest activity (the time of its last write), not the one that was created last. `--resume <id>` finds the id in every directory and loads the session in the directory it belongs to. `--resume <title>` matches the title, which is the first message of the session, among the sessions of this directory, without regard to letter case and to spaces at the ends; two sessions with the same title are an error that lists their ids and last activity. `--session-id <id>` reads every page of the session list and refuses an id that any session has (`Session ID <id> is already in use.`, exit status 1); that costs one pass through the list (`scripts/session_list_bench.py` prints it as `walk all`), and an agent that offers no `session/list` skips the check and refuses a used id itself. The lookup stops after 30 s, the limit of the connect (`GROK_CONNECT_UI_TIMEOUT_SECS`). A session in which nobody typed has no file now, so `--continue` cannot take it (see the next entry). **Not solved, and left as it is**: the agent lists its session directory again for each page, so reading all pages costs pages × directory size, which grows faster than the number of sessions. `scripts/session_list_bench.py` (median of 3, Linux / Windows): `--session-id` takes 1.3 s / 1.8 s at 1,000 sessions and 28 s / 34 s at 5,000, which is over the 30 s limit on Windows; `--continue` takes 0.6 s / 0.8 s at 1,000 and 10 s / 12 s at 5,000. The owner decided that this is fine below 1,000 sessions (plan decision 18). Tests: 25 unit tests of the lookup against a scripted agent, 4 of the time limit and of a cancel, 3 end-to-end tests against the real agent, and `scripts/tui_pty/resume_matrix.py --strict` (13 of 13 pass; cases 5 and 11 were known gaps, and case 8 now needs exit status 1).
- **The agent writes the file of a session with its first message (`pi-agent-cli`, `pi-agent-harness`)**: the agent used to write the file of a session when it answered `session/new`. A run in which nobody typed a message left a file with the title `(no messages)`. That file stayed in the `/resume` list, and `zypi --continue` took it when it was the latest session of the directory. Now `session/new` makes the session in memory only. The file is written with the first message of the user, in one write: the header, the entries that were made before the message (for example a model change), and the message. A session in which nobody typed has no file. `session/list` does not show it. `session/load` and `session/resume` open its id again, empty (see the entry in **Fixed**). A client that has the session open can keep using it. **Behaviour changes**: `zypi` with no flag starts no session until the first message; `zypi --session-id <id>` and `/new` start one at once, with no file. An id that a client chose (`_meta.sessionId`) stays reserved while its session is open in the agent, so a second `session/new` with that id is refused (`invalid_params`) although no file has it. If another agent process saves a session with that id first, the first prompt of the session is refused (`a session with this id already exists`). This narrows the gap between two agent processes. It does not close it. Files that earlier versions wrote keep the title `(no messages)`. **For library users**: `JsonlSessionRepo.create({"deferred": True})` returns a `DeferredJsonlSessionStorage`, and its `written` property says whether the file exists. `create` without `deferred`, and `fork`, write at once as before. Tests: 10 for the storage (what is written and in which order, a failed write and its retry, two first messages at once), 6 new ones for the agent (the ACP contract and the chosen ids), and the older tests that expect a session in the list now send a message first. `scripts/tui_pty/resume_matrix.py --strict` has 16 cases (13 before). Two of the three new ones fail against an agent that writes at once: `--session-id` and `/new`, each left with no message. The third types a message after `/new`.
- **A resumed session no longer takes the sandbox profile it was created with (TUI)**: the old Rust agent saved the sandbox profile in the files of a session. `zypi --continue` and `--resume` read it back before the sandbox was applied, so a resumed session kept its sandbox, and `--sandbox X` on a session that was saved with `Y` was refused (`cannot resume this session under sandbox profile ...`). The Python agent never saved a profile, so for its sessions nothing changes. The profile now comes from `--sandbox`, from `GROK_SANDBOX` and from the configuration, as it does for a new session. The code that read it is gone (decision 2 of the plan).
- **`TUI CI` and `scripts/tui_baseline.py` run the Rust tests with `cargo nextest` (TUI)**: `cargo nextest` runs each test in a process of its own. `cargo test` runs all tests of a test binary as threads of one process, where they share the environment variables, the working directory and every `static`. The vendored tests were written for nextest, and some of them are reliable only under it. So the failures of this class cannot occur in CI now, also for a test that someone writes later. `scripts/tui_baseline.toml` has `[test] runner = "nextest"`, and the option `--runner cargo` takes libtest back. The runner reads the output of nextest (the `Summary` line, and the list of the tests that did not pass), so CI installs a pinned version (`nextest@0.9.148`, with `taiki-e/install-action`); the job is now named `cargo nextest (Linux x86_64)`. Three differences to know. nextest counts the `#[ignore]` tests and the tests that a `--skip` filter removes together as skipped (22 for the whole list, where `cargo test` printed 21 ignored). nextest does not run doctests, and these suites never ran them (the runner selects explicit `--lib`, `--test` and `--bin` targets). A suite that hangs is stopped with SIGTERM first and with SIGKILL after 20 s: nextest puts each test in a process group of its own, so SIGKILL alone left the hanging test running. 21 new `pytest` tests cover the parser, the commands, the choice of the runner and the stop signals. **CI result**: the first run of the whole tree under nextest passed: 8,490 passed, 0 failed, 22 skipped, and every suite equals its reference number (the 14 tests of `python_agent_e2e` ran too). The tests take about 130 s (the `Summary` times of nextest, added up), where `cargo test` took about 65 s for the same code. The job took 36 min 17 s, against 33 min 56 s for a `cargo test` job that started 4 minutes earlier. The time of the job varies from 17 to 34 min between runs of `cargo test`, so the added test time (about 65 s) is the cost that this change causes.
- **The notice about MCP servers names only the servers that nobody took over (`pi-agent-cli`)**: it said "This agent does not connect to MCP servers, so the 1 MCP server the client passed (...) were ignored", which was wrong in number, and it counted every server. Now it says "The client passed 1 MCP server (...). This agent does not connect to MCP servers by itself, so its tools are not available in this session. To use it, install the pi-mcp-py package.", with "it" and "its" for one server and "them" and "their" for more. When the `pi-mcp` entry point is installed but no extension claimed a server, the notice says that no extension took the server over, and it does not tell the user to install anything. The log line is the same as before (names only). The 0.5.0 notes call the decision "a Phase 4 non-goal". Phase 4 did not discuss MCP; the decision is from Phase 6.
- **`HarnessBridge` has four more members (`pi-agent-core`)**: `client_mcp_servers`, `claim_client_mcp_servers`, `notify` and `add_turn_barrier`. `HarnessBridge` is a runtime-checkable protocol, so a custom bridge (a test double, say) must add them to pass `isinstance`. `AgentHarness` is the only bridge in this repository.
- **New version numbers (all Python packages, TUI)**: `pi-agent-core-lc`, `pi-agent-harness-lc` and `pi-agent-cli-lc` go from 0.5.0 to 0.6.0. The three pin each other with `==`, so install them at one version. `zypi --version` and the `agentInfo` of the agent show 0.6.0 (the `Cargo.toml` files of `pi-pager-bin` and `pi-version` and `tui/Cargo.lock` carry the version of `pi-agent-cli-lc`, and a test checks it). The extension packages are released with the core, so all four now require `pi-agent-core-lc>=0.6.0`, and `pi-dynamic-workflows-py` also requires `pi-agent-harness-lc>=0.6.0`. `pi-web-access-py`, `pi-goal-x-py` and `pi-dynamic-workflows-py` go from 0.2.0 to 0.3.0. Their code has not changed since 0.2.0; only the requirement is new. The publish step skips a version that is on PyPI already, so a new requirement needs a new version number. `pi-mcp-py` is new and stays at 0.1.0.

### Removed

- **The code in the TUI that read session files**: `materialize_startup` and its helpers, the pin of `--resume <title>` before the sandbox (`pin_local_resume_target`), the saved sandbox profile (`SandboxStartup`, `saved_resume_profile`), the check that a `--session-id` is free before `session/new`, the first-prompt fallback of the resume picker (it read `chat_history.jsonl`), the check of the session files in the picker's load, and the read of `<home>/sessions/.../plan.md` for the plan preview. `scripts/tui_baseline.py gates` has a new gate (`gates.session_disk_reads`): it fails when production code in `pi-pager` or `pi-pager-bin` calls the readers of the session store again.
- **The session store of `pi-shell`, and the code that only it used (TUI)**: `pi-shell` still held the code that wrote and read the session files of the old Rust agent (`session::storage` and `session::persistence`). Since the change above, no code in `zypi` calls it. It is deleted. ### Known issues

- **Some flags and settings have no effect**: in the interactive UI, `--system-prompt-override` and `--rules` do nothing, and `--allow` and `--deny` do not reach the agent. `zypi --help` still lists flags from the upstream project that nobody has checked one by one. On the settings page, the items other than the permission mode may have no effect with the Python agent. `remember_tool_approvals` and `default_selected_permission` were not tested.
- **`[ui.status_line]` has no `context` or `cost` items with the Python agent**: the agent does not tell `zypi` the size of the context window, the tokens in use or a cost, so these items stay empty, and a script gets no `context_window.*`, `cost.total_cost_usd`, `workspace.branch` or `workspace.repo_root`. The rest of the row is drawn.
- **The user guide has no way to open it**: the 7 pages are in the binary, but nothing in the UI opens them.
- **`--session-id` and `--continue` get slow with thousands of sessions (TUI, `pi-agent-cli`)**: the agent lists its session directory again for each page of `session/list`, so reading all pages costs pages × directory size. `--session-id` reads all pages. At 1,000 sessions it takes 1.3 s on Linux and 1.8 s on Windows. At 5,000 sessions it takes 28 s and 34 s, and the lookup stops after 30 s. `--continue` takes 0.6 s and 0.8 s at 1,000 sessions, and 10 s and 12 s at 5,000. Below 1,000 sessions this is fine, and the owner decided to leave it (plan decision 18).
- **Two agent processes that use one home can still make two sessions with the same id (`pi-agent-cli`)**: inside one agent process, an id that a client chose is reserved while its session is open, so a second `session/new` with that id is refused. Two processes do not see each other's reservations. Both can make the session; the first to write its file wins, and the first message of the other is refused (`a session with this id already exists`).
- **An id that no session ever had also opens with `session/load` (`pi-agent-cli`)**: the agent cannot tell such a UUID from the id of a blank session (a session with no file), so it opens an empty session. `zypi export <uuid>` of such an id says that the session has no conversation content, and not "not found".
- **`pi-mcp-py` is Alpha (0.1.0)**: it has no OAuth, MCP resources, prompts, sampling, roots, elicitation or `tools/list_changed`. The MCP SDK hides the error of a failed POST request of a legacy SSE server, so a call to a dead SSE server ends only after the call limit of 120 s. A thread that Zed creates before the first worktree of the project has loaded gets an empty `mcpServers` list (zed#64611). The agent cannot tell this from "no servers", so such a thread has no MCP tools and no notice; a new thread works. `zypi` has no setting for MCP servers, so only an editor can pass them. The package takes the `annotations` of a server as given: in the `ask` mode, a tool that its server marks as read-only runs without a question. Nobody has used the package in the real Zed window; its tests use real child processes, the real agent and ACP over stdio.
- **Tested on Linux only for the latest changes**: the end-to-end and pseudo-terminal scripts run on Linux (WSL2); the tests of `pi-mcp-py` also run on Windows. Nobody has started the macOS binary (CI builds it). There is no Windows binary. The Landlock layer of the sandbox was not tested: the kernel of the test machine (5.10) has none.
- **Open findings in the Python packages**: the low-risk findings F7-02 to F7-09 of the Phase 6 and Phase 7 audit have no fix yet (small defects in the extension API, and notes for the specs). See `docs/AUDIT/AUDIT-PHASE6-PHASE7-2026-09-30.md`, section 8.

## [0.5.0] - 2026-10-13

`zypi` no longer has an agent of its own. It draws the terminal screen and talks ACP to the Python agent (`python -m pi_agent_cli`), and that agent is now the only agent. **Removed** says what went with the Rust agent runtime. **Known issues** says what does not work yet. This release also has the Phase 6 and Phase 7 changes to the Python packages: project trust, a sandbox for workflow scripts, DeepSeek thinking with tools, and tool annotations.

### Added

- **Project trust (Phase 7)**: a project's own extensions, saved workflows (`.pi-python/workflows`), `.pi/SYSTEM.md`, `.pi/APPEND_SYSTEM.md` and project-relative `[skills].paths` are now used only once the user has vouched for the project; before, opening a repository imported its extensions and turned its saved workflows into slash commands. `[extensions] default_project_trust = "ask"` (the default; or `"never"` / `"always"`) has the ACP client answer a `session/request_permission` (`Don't trust` / `Trust and remember`; no `allow_once`, so a client that auto-approves tool calls cannot answer it) before anything of the project loads. The answer is saved in `~/.pi-python/agent/trust.json` with a `sha256:` fingerprint of the files, so a `git pull` that changes them asks again. `trusted_projects`, `trust_project_extensions = true`, `--trust-project-extensions` and `PI_TRUST_PROJECT_EXTENSIONS=1` also trust; headless (`-p`) runs never ask but honour a saved answer that still matches. Extensions read the answer as `pi.project_trusted`; library users pass `AgentHarness(trust_project_extensions=True)`. **Behaviour change**: ACP sessions in such projects now ask (`default_project_trust = "never"` keeps the old silent skip). Not covered: a client may auto-approve the request, files changed after the session started are not re-checked, and `AGENTS.md` / `CLAUDE.md` are not gated (as in upstream pi). Design: Phase 7 spec, sections 4.4 and 16.
- **Workflow scripts run in a process of their own, under limits the operating system enforces (Phase 7)**: scripts used to be `exec`'d in the host's interpreter, where the narrowed `__builtins__` had two known ways out and a `while True` froze the host's event loop. Each `WorkflowRuntime.execute()` now starts a child process with an empty environment; the host does everything with an effect (sub-agents, journal, logs, budget) over a JSON-lines pipe and treats the child as hostile. The kernel limits the child (rlimits on POSIX, plus `no_new_privs` and no `fork` on Linux; a Job Object and a lowered integrity level on Windows), and `WorkflowRuntime(sandbox_limits=SandboxLimits(...))` sets them (an optional wall-clock deadline among them). **What this is not**: the audit hook is a speed bump, and what the kernel still allows differs per platform (a script can still read the files the user can read and use the network), so run the agent in a container if scripts cannot be trusted. **Behaviour changes**: values cross the process boundary as JSON, `budget` in a script is read-only, a run costs a process start (about 0.06 s on Linux, 0.14 s on Windows), Windows needs the default event loop, and `execute()` raises `WorkflowScriptError` for a script that raises and a `SandboxError` for one that is stopped. Design: `docs/specs/2026-10-01-workflow-sandbox-design.md`.
- **DeepSeek thinking works together with tools (Phase 6)**: with thinking on, DeepSeek's own API answers 400 to a request with tools unless earlier assistant messages bring their `reasoning_content` back, which `ChatDeepSeek` leaves out. The adapter now keeps it and sends it back on every assistant message (`adapters/deepseek_replay.py`), and it states whether to think (`thinking: enabled | disabled`, `reasoning_effort`) instead of leaving it to the API's default (on). Both apply to DeepSeek's own API only (no `base_url`, or one on `deepseek.com`), not to gateways serving DeepSeek models. **Behaviour change**: with the default `thinking_level="off"`, requests now send `thinking: disabled`; code that relied on the old default to get reasoning blocks must set `Model.reasoning=True` and a `thinking_level`. Not verified against the live API (no key). Spec: Phase 6, section 5.5.
- **`[model] reasoning` in `agent.toml` (Phase 6)**: whether the configured model can reason (`Model.reasoning`); unset, any `thinking_level` other than `off` says it can. This is what makes `thinking_level` take effect through the CLI, which built every model with `reasoning=False` (the level was dropped on OpenAI and Anthropic). A model that rejects reasoning parameters needs `reasoning = false`.
- **Tools can declare what they do: `ToolAnnotations` (Phase 7)**: MCP's four hints (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`; a tool that declares nothing claims nothing). `SimpleTool`, `CodingTool` and `ToolDefinition` take `annotations=`, `from_langchain_tool` reads them from `tool.metadata`, and `tool_call` hooks receive them as `ToolCallEvent.annotations`. Built in, `read`, `grep`, `find`, `ls`, `web_search` and `fetch_url` declare themselves read-only, `goal_update` and `goal_complete` neither destructive nor open-world, and `bash`, `edit`, `write` and `workflow` declare nothing, on purpose. The hints are the tool author's word and are not verified; `ask` mode uses them (see Changed). Design: Phase 7 spec, section 12.
- **The TUI keeps the agent's stderr**: `zypi` points its own stderr at `/dev/null` and the agent inherited it, so a Python traceback or warning from the agent went nowhere. It is now appended to `<home>/logs/agent.stderr.log` (mode 0600 on Unix, one `--- agent started ... ---` line per run, moved to `agent.stderr.log.1` once it is over 1 MiB at the next start). `zypi -p` is unchanged: the agent's stderr stays on the terminal.
- **A sandbox that cannot be put in force says so (TUI)**: on a kernel without Landlock (Linux before 5.13, or with it disabled) `zypi --sandbox <profile>` used to start without the file and network limits and without a word; the only trace was an `ApplyFailed` line in `sandbox-events.jsonl`. It now prints a warning on stderr at start-up and shows `sandbox:<profile> (not enforced)` in the welcome page's top bar and the status bar, where the label of an applied profile is drawn. Where the sandbox is applied nothing changes.
- **`session/list` comes in pages (`pi-agent-cli`, `pi-agent-harness`)**: the agent answers with at most 50 sessions, newest first, and a `nextCursor` while more follow; the cursor is opaque, carries the position in it (the agent keeps nothing between requests, so it survives a restart) and anything the agent did not issue is `invalid_params`. The TUI keeps asking until the cursor is gone, so its session picker still lists everything. For library users `JsonlSessionRepo.list_page(...)` returns one page and `JsonlSessionRepo.find(id)` reads one session's header instead of the directory. With 1,000 sessions of 120 entries on Windows, the first answer took 2.0 s and a `session/load` of one of them 2.0 s; reading a file's first line no longer reads the file and a lookup by id no longer lists the directory, which makes them 0.11 s and 0.12 s (`scripts/session_list_bench.py`; numbers and method in `docs/PLAN/archive/PLAN-RUST-AGENT-RUNTIME-REMOVAL-EXECUTION-LOG.md` §10.11). `updated_at` is still the file's mtime and need not follow the list's order, which is by creation time.
- **The agent says which MCP servers a session ignored (`pi-agent-cli`)**: the agent connects to no MCP server (a Phase 4 non-goal), which departs from ACP's "an agent MUST support stdio servers"; `session/new`, `load` and `resume` used to drop the list without a word. Each session set up with a non-empty list now logs a warning and sends one agent message naming the servers (names only: `env`, `headers`, `args` and `url` hold tokens). `zypi` no longer forwards what it finds in `.mcp.json`, `~/.claude.json` and Cursor's `mcp.json`, so there the message never shows; it is for other ACP clients, an editor that passes its own servers, say.
- **A client can choose the id of a new session, and the agent says which directory a session works in (`pi-agent-cli`, `pi-agent-harness`)**: `zypi --session-id <uuid>` has always sent the id in `session/new`'s `_meta.sessionId`; the agent ignored it and picked its own, so the flag did nothing on the Python agent. It now becomes the session's id. It must be a UUID in any form `uuid.UUID` reads (kept as lower case with hyphens); anything else is `invalid_params`, because the id ends up in a file name. An id some session already has is refused with `invalid_params`, whatever directory that session belongs to, and two requests for the same id at once make one session. `session/new`, `load` and `resume` answer with `_meta["pi/cwd"]`, the directory the session works in; for `load` and `resume` the one saved with the session wins over the `cwd` the client sent. For library users `JsonlSessionRepo.has_session(id)` says whether an id is taken and opens only the files whose names do not already say they belong to another session (`find` reads every header for an id nobody has). A free id costs the directory listing: 0.07 s at 1,000 sessions, 0.3 s at 5,000, on Windows and WSL2 alike (`scripts/session_list_bench.py`). **Not yet in the TUI**: `zypi` still checks for a used id in the old session layout, so it never sees the Python agent's sessions; the agent refuses the id and the TUI shows `Session creation failed: Invalid params: {...}` instead of exiting 1 with a message (`scripts/tui_pty/resume_matrix.py`, case 11), and nothing reads `pi/cwd` yet (execution log section 10.11, ADR1 PR 2).

It says: 305,581 lines of non-test code in the 7 support crates, and 17 modules (6,190 lines, 4,339 of them in `pi-hooks`) that no live code refers to. A module on that list is a candidate for deletion, not proof, so the list was checked with the compiler. In a copy of `tui/`, 16 of the 17 modules were deleted, and `cargo check` passed (also `cargo check --workspace --tests`, after the test file of the removed `pi-hooks` modules went too). The 17th, `types::error` in `pi-tools`, cannot go: it holds the `impl From<…> for ToolError` that `?` calls, and no path names it. The tool marks such modules "check first". The first version listed 21 modules and 4 of them were live: it did not see a path inside an attribute string (`serde(with = "crate::util::serde_base64")`) or a path that starts at a child module. Both are fixed. 39 tests; each of 17 changes made to the tool makes a test fail. Nothing was deleted from `tui/` (plan item D.8; execution log section 10.14).
- **A check that `tui/THIRD-PARTY-NOTICES` matches the dependencies (`scripts/tui_notices.py`)**: the file came from the upstream project and did not follow `Cargo.lock`. `check` finds the packages that ship in `zypi` (the normal and build dependencies of `pi-pager-bin`, for five target triples, from crates.io, git or `tui/third_party/`) and exits 1 if an entry is missing or stale. `update --write` fixes the file: it removes stale entries, adds missing ones and leaves the hand-written parts and the license texts alone. The license wording of a new entry is copied from the entries with the same SPDX expression; a package with no such entry is listed as `needs review`. First run: 222 stale entries removed (packages that are not in the binary) and 44 missing entries added, so there are 989 entries for 989 packages, and the file went from 18,898 to 16,548 lines. None of the 44 needed review. This matches the file to `Cargo.lock`. It is not a legal review: nobody has read the copied wording one entry at a time. `check` needs `cargo`. 62 tests.
- **A network audit of `zypi` (`scripts/tui_pty/net_audit.py`, Linux)**: it runs `zypi` in a pseudo-terminal, plays one turn, and reads the sockets of `zypi` and of every process below it about every 9 ms (`/proc/<pid>/fd` joined with `/proc/<pid>/net/{tcp,tcp6,udp,udp6}`). `zypi` must hold no connection to a non-loopback address and must listen on none. ### Fixed

- **A saved workflow whose `meta` description was not text made every `session/prompt` fail (`pi-dynamic-workflows`, Phase 7)**: the value reached the command list unchecked, `AvailableCommand` refused it, and the list is re-sent with every prompt until a send succeeds. Now `WorkflowStore` drops a non-string `description` / `when_to_use`, `ExtensionAPI.register_command` raises `TypeError` for one (that extension is rolled back like any failed one), and `PiAcpAgent` leaves out a command the schema rejects, with a warning, and sends the rest.
- **The pi home was resolved differently in different places (Phase 7)**: only the CLI honoured `PI_HOME`, and `PiAcpAgent(home=)` / `run_print(home=)` did not hand their home on, so a session could read its config from one directory and its extensions, saved workflows and journals from another. One resolver, `pi_agent_core.home.pi_home` (argument, `$PI_HOME`, `~/.pi-python`), now serves the CLI, `ExtensionLoader`, `AgentHarness(home=)`, `ExtensionAPI.home` (`pi.home`), `WorkflowStore(pi_home=)` and `create_workflow_tool(home=)`. With the working directory set to the home directory, `~/.pi-python/extensions` is no longer imported twice.
- **`<git_status>` (Phase 6)**: git's output was decoded with the locale codec, so on non-UTF-8 locales (cp936 on Chinese Windows) a branch such as `功` failed the turn; git now runs with `encoding="utf-8", errors="replace"` and `core.quotePath=false`, and any failure omits the section instead. A repository with no commit yet lost the section; it now shows `Branch: main (no commits yet)`. The snapshot ran up to three `git` processes on the event loop; it is now built in a worker thread, and `[git] timeout_seconds` is one budget for the whole snapshot.
- **`tool_call` hooks can no longer overturn a denial**: an extension registered after the permission layer could un-deny a call by returning `{}` or `{"block": False}` (the last non-`None` verdict won). Dispatch now stops at the first blocking verdict, like upstream pi's `emitToolCall`.
- **Extension tools in the system prompt**: `prompt_snippet` / `prompt_guidelines` of extension-registered tools (`workflow`, `goal_update`, `web_search`, ...) were never rendered by the CLI. `pi-goal-x`'s guidelines were reworded to hold when no goal is active.
- **Sub-agent model routing and credentials (`pi-dynamic-workflows`)**: a `tier` resolved to an Anthropic model whatever the parent ran on, and the one configured API key was handed to every provider (a DeepSeek session sent its key to Anthropic). `resolve_tier(tier, tiers=None, *, provider=None)` now uses per-provider defaults (`DEFAULT_MODEL_TIERS_BY_PROVIDER`, `anthropic` only; `DEFAULT_MODEL_TIERS` is removed), so under another parent provider a `tier` inherits the parent model. `make_get_api_key(config)` returns the key only for `config.provider` (export the other provider's own variable, e.g. `ANTHROPIC_API_KEY`, when a workflow routes there), and a sub-agent model keeps the parent's `base_url` only on the parent's provider.
- **`workflow` sub-agents ran `bash` / `edit` / `write` without asking (`pi-dynamic-workflows`)**: the permission layer is a `tool_call` hook on the session's harness, which the sub-agents' fresh harnesses did not have, so in `ask` mode a script could write files and run commands unprompted (and `workflow` itself was not gated). `workflow` is now permission-gated and every sub-agent tool call goes through the parent session's `tool_call` chain (`AgentHarness.check_tool_call`, exposed to extensions as `HarnessBridge.tool_call_gate`; fail-closed), with `ToolCallEvent.origin` telling the prompt where the call comes from.
- **Two extensions defined in one module replaced each other (Phase 7)**: an extension's name was `activate.__module__`. A module-level `activate` is still named after its module; any other callable is now `module.qualname`, and `AgentHarness.load_extension(activate, *, name=None)` takes an explicit name. Loading under a taken name still replaces, but warns when the replacement is a different callable.
- **A failing extension vanished without a trace the user could see (Phase 7)**: import errors, an entry point that resolves to nothing and an `activate()` that raises are now recorded (`ExtensionLoader.failed`, `AgentHarness.failed_extensions`) and reported by the CLI (an ACP agent message after `session/new`; headless stderr).
- **An invalid tool name broke every later request (Phase 7)**: providers accept only `[a-zA-Z0-9_-]{1,128}` and reject the whole request otherwise. `register_tool` now refuses other names and rolls that extension back.
- **`workflow` ran against canned answers when sub-agents could not be built (`pi-dynamic-workflows`)**: the extension quietly fell back to `MockSubagentExecutor`, so a script "completed" with fake results. It now registers `UnavailableSubagentExecutor(reason)`, and the tool answers "The workflow tool cannot run in this session: sub-agents are unavailable (<reason>)."
- **Workflow run ids and saved-workflow names accepted a trailing newline; a non-dict `meta` broke the directory scan (`pi-dynamic-workflows`)**: both patterns ended in `$` and are now matched with `fullmatch`; `meta = 5` in one saved script no longer raises out of the whole scan.
- **`resume_from_run_id` replayed nothing after a parallel run, and recorded failures as answers (`pi-dynamic-workflows`)**: the journal matched calls by position, but `parallel()` records in completion order, and a failed `agent()` was written as a successful `None`. The journal is now a request-keyed cache: a call gets the earliest recorded answer to the same request that this run has not used yet, and a failure is not recorded, so a resume retries it.
- **Cancelling a foreground `workflow` did not stop it (`pi-dynamic-workflows`)**: the tool never looked at the abort signal, so the remaining sub-agents kept spending tokens and editing files. The run is now raced against the signal: on abort it is cancelled (up to 10 s to unwind), its worktrees are removed, and the tool answers "cancelled" with the `run_id` and how to resume. Background runs are deliberately not tied to the turn that launched them.
- **Sub-agent worktrees lost new files, corrupted non-UTF-8 files and leaked (`pi-dynamic-workflows`)**: the patch came from `git diff HEAD` (no untracked files) and was decoded as text (an edit to a GBK file failed with `patch does not apply`); a worktree also leaked when its sub-agent failed early, timed out or was cancelled. The patch is now `git add -A` + `git diff --binary --cached HEAD`, kept as bytes, and every path removes its worktree.
- **Closing a session left its work running, and a background workflow's result woke the dead session (Phase 7)**: `AgentHarness.close()` now aborts the turn in flight, runs every cleanup callback (a failing one no longer stops the others) and stops the turns it started for extensions; afterwards `prompt()` raises `AgentHarnessError("invalid_state")`. `WorkflowManager.close()` cancels background runs and delivers nothing afterwards. ACP `session/close` and `pi/session/delete` (which did not call it) both go through `close()`.
- **A background workflow's output entered the conversation as if the user had typed it (Phase 7)**: the result (text from sub-agents that may have read untrusted files or pages) was injected as a user message and would have run as a slash command had it started with `/`. It is now delivered with the new `HarnessBridge.trigger_message(custom_type, text, *, details=None)` as a typed `workflow-result` message (never slash-dispatched) inside a `<workflow-output boundary=...>` envelope that declares it untrusted data. That is a convention the model may or may not honour, not isolation.
- **`fetch_url` fetched anything it was pointed at, without limits (`pi-web-access`, Phase 7)**: the model chooses the URL, yet the tool followed redirects to any address (the cloud metadata service, `localhost`), read whole responses into memory, and crashed on its own truncation notice, so a page over 50 KB came back as `Failed to fetch ...`. Now only `http(s)` URLs on the public internet are fetched: private, loopback, link-local and reserved addresses, `localhost`, `*.local`, `*.internal`, single-label names and URLs with credentials are refused however they are spelled, and so are redirects to them (at most 5 are followed), with `Refusing to fetch ...: ...` and no request. Without a proxy the name is resolved once and the checked address used; through a proxy only literal addresses can be checked. The body is cut at 5 MiB and a call takes at most 30 s. **Migration**: to read a service on this machine or the intranet, use a tool the user authorises for it (`bash` with `curl`, say). Details: Phase 7 spec, section 5.3.
- **`pi-goal-x`: a finished goal came back unfinished, a wrong step index invented a step, and a reminder repeated without end (Phase 7)**: the goal is now saved whenever it changes, so a resumed session no longer reactivates a finished goal; `update_step` with an index that names no step raises `ValueError` naming the steps that exist (it appended an `Unnamed step`), and the status lists steps as `[0]`, `[1]` to match the 0-based `step_index`; the reminder to call `goal_complete` is sent at most twice. API: `create_goal_update_tool` / `create_goal_complete_tool` take an optional `on_change` callback, `GoalState` gains `reminders_sent`, and the `turn_end` hook no longer saves the goal.
- **Provider matrix and live tests (Phase 6)**: the `deepseek` row used `deepseek-chat`, a non-thinking alias DeepSeek retired on 2026-07-24; it now uses `deepseek-v4-flash` (`MATRIX_DEEPSEEK_MODEL` still overrides). `real_llm` tests were meant to be deselected by default but only skipped when their key was unset, so an exported `OPENAI_API_KEY` made a plain `pytest` pay for API calls; `pyproject.toml` now sets `addopts = "-m 'not real_llm'"` (run them with `pytest -m real_llm ...`). The `provider-matrix` workflow also runs weekly.
- **A prompt sent while a `workflow` result was being worked on failed with `busy` (Phase 7)**: the result of a background `workflow` starts an LLM turn with no `session/prompt` behind it, so the client could not know the session was occupied. `session/prompt` now waits for that turn and then runs (`session/cancel` or closing the session ends the wait); a second `session/prompt` from the same client while one is in flight is still `busy`. ACP's `state_update` is deliberately not sent: it exists only in the unstable protocol v2 draft, which neither the Python SDK nor the TUI's Rust crate can read. Spec: Phase 7, section 13.
- **`zypi` told the user nothing when the agent failed to start or died**: a missing agent program surfaced as `channel closed ... recv_failed`, and an agent that exited as soon as it started (a Python without `pi_agent_cli`, say) left `connect` waiting forever; an agent that died in the middle of a turn left the requests in flight waiting too. The stdio bridge now notices the exit and says what happened: the program, its exit status and the last lines the agent wrote to `agent.stderr.log` (`failed to spawn ACP agent ... PI_AGENT_COMMAND` for a program that is not there). `zypi`'s exit status is unchanged. Found by the new end-to-end suite that runs the pager's ACP client against the real agent (`tui/crates/codegen/pi-pager/tests/python_agent_e2e.rs`; TUI CI installs the agent for it).
- **`zypi -p` left the agent and its tools running when only `zypi` was killed**: `kill <pid>`, `kill -9`, `timeout` or an IDE's stop button reached `zypi` but not the agent, which kept running (and kept running its `bash` call) on the user's terminal. `zypi` now passes its pid in `PI_AGENT_PARENT_PID`; `python -m pi_agent_cli -p` watches its parent and stops the way it stops on a signal (turn cancelled, tools reaped), and `-p` now handles SIGTERM and SIGHUP too (exit status 128 + the signal number). POSIX only; the variable is removed from the environment at start-up, so tools do not inherit it, and it is ignored when it names a live process that is not the agent's parent (a wrapper script).
- **`zypi --sandbox ...` on Linux left the whole process tree running when only the outer `bwrap` was killed**: the sandbox re-launches `zypi` under `bwrap`, which by default just waits for its child, so signalling the process the shell started (`kill $!`, a supervisor) left `zypi`, the agent and its tools on the terminal. `bwrap` now runs with `--die-with-parent`. **Trade-off**: a SIGTERM or SIGHUP sent to that outer `bwrap` now reaches `zypi` as SIGKILL, so the terminal is not restored (alternate screen, raw mode); before, the tree kept running instead.
- **Messages in `zypi` that pointed at files that do not exist**: five messages (four from the MCP config code, one from the sandbox glob code) ended with `See ~/.grok/docs/user-guide/<page>.md`, a path that `zypi` never uses; the help of `zypi wrap` ended with `See ~/.pi-python/README.md for more information.`, and there is no such README; and the footer of the document picker named the folder where `zypi` used to write the pages. The pointers are gone.
- **Quitting `zypi` while the agent ran a tool left the tool running (TUI, `pi-agent-cli`)**: `zypi` killed the agent with SIGKILL at once, so the agent could not stop the process group of a running `bash` call (after a double Ctrl+Q, a `sleep 300` kept running). `zypi` now closes the agent's stdin, waits up to 3 s for the agent to exit, and kills it only after that. The agent treats SIGTERM and SIGHUP like the end of its input: it cancels the turn and stops its tools. A second signal takes the default action, so an agent that hangs while it stops can still be killed. This also covers `kill -9` on `zypi`, where the kernel sends SIGHUP to the foreground process group. In a pseudo-terminal on Linux and on macOS, a double Ctrl+Q, `kill -9`, `kill -TERM`, closing the terminal and Ctrl+C left no tool process. Windows has no such test.

The agent now sets the flag.
- **`session/list` gave no useful title and a wrong time (`pi-agent-cli`)**: the title of each session was its creation time and a short id, and `updated_at` was the creation time. The title is now the first user message (white space collapsed, 100 characters at most; `(no messages)` when there is none), and `updated_at` is the time the session file was last written. So the `/resume` picker shows readable titles.

The agent now compares the file itself (device and inode), so a hard link counts as the same file. The error was there since Phase 5 (v0.3.0).
- **`zypi doctor fix ssh-wrap` wrote an alias for a command that does not exist (TUI)**: the block in the shell's rc file said `alias ssh='grok wrap ssh'`, so after the fix every `ssh` call failed. It now writes `alias ssh='zypi wrap ssh'`, and the block marker is `# >>> zypi doctor >>>`. **Migration**: the new version does not know the old block. If you ran the fix before, delete the old block from the rc file by hand.
- **Messages in `zypi` named a directory and commands that do not exist (TUI)**: they said `~/.grok` and `$GROK_HOME` where the real names are `~/.pi-python` and `$PI_HOME`. They told the user to run the slash commands `/doctor`, `/minimal`, `/fullscreen` and `/copy`, and the commands `grok wrap` and `grok worktree gc|rm`, and none of these exists. They now name `zypi doctor`, `zypi wrap ssh <host>`, `zypi --minimal`, `zypi --fullscreen` and the real directory.

### Changed

- **`agent(..., cwd=)` is limited to the project (Phase 7)**: a workflow script could point a sub-agent at any directory; the permission prompt showed it, nothing stopped it. The directory must now be inside the project (`WorkflowRuntime.cwd`; relative paths are read against it, symbolic links and junctions resolved first): a path outside is a `ValueError` the script can catch, a non-string a `TypeError`. `HarnessSubagentExecutor` checks again before creating a worktree. **Migration**: a script that used `cwd` to leave the project has to be rewritten. Design: `docs/specs/2026-10-01-workflow-sandbox-design.md`, section 8.1.
- **`ask` mode asks about every tool call unless the tool declares itself harmless (Phase 7)**: the permission layer used a fixed set of names (`PERMISSION_TOOLS`), so every other tool, in particular every tool an extension registers, ran without a question. Not covered: the hints are not verified, and a caller who connects MCP servers it does not trust must remove their annotations before `from_langchain_tool`. Design: Phase 7 spec, section 12.

The `GROK_*` environment variables, the project path `.grok/sandbox.toml` and the `grok_home` field of `zypi du --json` keep their names: a rename of these would break existing setups, so it needs its own decision.
- **`zypi --version` and the ACP `agentInfo.version` show the version of the release (TUI, `pi-agent-cli`)**: `zypi --version` printed `1.0.8`, the version of the upstream project, and the agent reported `0.1.0` whatever the package was. `zypi` now prints `0.5.0` (the version in the `Cargo.toml` of `pi-pager-bin` and `pi-version`), and the agent reports the version of the installed `pi-agent-cli-lc` package. A test fails if those two crates or `Cargo.lock` differ from the version of `pi-agent-cli-lc`, so raise them together with the Python packages at each release. The release workflow does not set `GROK_VERSION`, on purpose: the same variable marks a build as a release build and turns the folder-trust prompt on, and a test fails if a workflow sets it. **Behaviour change**: the number is lower than before. A `[[version_overrides]]` patch in a config file whose `minimum_version` is above `0.5.0` no longer applies; none ships with `zypi`.
- **The status row is drawn with the Python agent (TUI)**: `[ui.status_line]` (`type = "builtin"` or `"command"`) drew nothing with the Python agent, because the row was built from a `session_status` message that only the old Rust agent sent. `zypi` now builds the row from what it knows itself: the working directory, the session id, the model, the session name, its own version, how long it has held the session (`cost.total_duration_ms`), and when the turn began (`turn.started_at_ms`). A status that an agent does send is read first, and `zypi` fills only the fields that the agent left out; the session name is always `zypi`'s own. The row is built again when the session, the model, the name, or the state of the turn changes, so a timer does not stay on the row after its turn. **What it does not show**: the agent does not tell `zypi` the size of the context window, the tokens in use, or a cost, so the `context` and `cost` items stay empty with the Python agent, and a script gets no `context_window.*`, `cost.total_cost_usd`, `workspace.branch`, `workspace.repo_root` or other field that only an agent can fill. A script that needs the branch runs `git` itself. Plan decision 15 first chose that the Python agent sends the status. The review that DESIGN section 8.5 asks for failed on two of its five points: what the agent could truthfully send is known to `zypi` already or has a standard place in ACP, and the type of the message would live in an old runtime crate. The user then chose this way: no new message on the wire, and no change to the Python packages. The guide page `25-status-line.md` and `scripts/tui_pty/status_line_probe.py` say what the row shows now. Tests: 16 new unit tests (what `zypi` fills in and what an agent status keeps, the two clocks, when the row is built again, and what a script is given), 2 tests rewritten that said the row waits for the agent, and `scripts/tui_pty/status_line_probe.py`, which now checks that the row is drawn and that a script gets the facts and no invented number (4 of 4 runs on a real `zypi`).

### Removed

- **The Rust agent runtime in `zypi` (TUI)**: `zypi` carried a second agent written in Rust. The Python agent was already the agent that `zypi` started by default. The Rust one is gone: the `pi-sampler` crate (31 files, 14,300 lines), most of `pi-shell` (the agent, sub-agents, sessions, the leader and relay processes) and the code in `pi-pager` that used them, with their tests. Since v0.4.0, `tui/crates` went from 2,500 Rust files and 1,620,612 lines to 1,755 files and 1,021,067 lines, and `tui/Cargo.lock` from 1,311 to 1,257 packages. The Linux release binary went from 470,461,776 bytes to 420,767,096 bytes. `zypi` needs the Python agent for everything: it starts `python -m pi_agent_cli`, or the command in `[agent].command` or `PI_AGENT_COMMAND`.
- **Screens, commands and flags that the Python agent cannot serve over standard ACP (TUI)**: an audit of every entry point removed the agent dashboard; the agents, extensions and persona dialogs; tasks, background and scheduled tasks; the sub-agent, workflow, goal and catalog panes; the shared prompt queue with its interject, send-now and steer actions; the MCP dialog and the import of Claude's MCP settings; hooks, plugins and the marketplace; rewind, fork, jump and external sessions; the recap, feedback, consent and data-sharing prompts; the "What's new" screen; session rename; and "New worktree" (the welcome-page item, and `ctrl+w` in the session picker). Of the slash commands, only `/settings`, `/new`, `/model`, `/resume`, `/theme`, `/multiline`, `/home`, `/help` and `/exit` are left. The flags `--fork-session`, `--leader`, `--no-leader` and `--leader-socket` are gone too. A script that uses one of them needs a change.

### Known issues

- **`--resume`, `--session-id` and `--continue` work only in part with the Python agent**: `--resume <title>` finds no session (`no session id or title matched`, exit status 1). `--resume <unknown id>` fails only after the UI has started. `--session-id <id>` with an id that is in use is refused by the agent, but the UI shows `Session creation failed: Invalid params: ...` and stays open. `--continue` takes the session that was created last, not the one that was used last.
- **Some flags and settings have no effect**: in the interactive UI, `--system-prompt-override` and `--rules` do nothing, and `--allow` and `--deny` do not reach the agent. `zypi --help` still lists flags from the upstream project that nobody has checked one by one. On the settings page, the items other than the permission mode may have no effect with the Python agent. `remember_tool_approvals` and `default_selected_permission` were not tested.
- **`[ui.status_line]` has no `context` or `cost` items with the Python agent**: the agent does not tell `zypi` the size of the context window, the tokens in use or a cost, so these items stay empty, and a script gets no `context_window.*`, `cost.total_cost_usd`, `workspace.branch` or `workspace.repo_root`. The rest of the row is drawn (see **Changed**).
- **The user guide has no way to open it**: the 7 pages are in the binary, but nothing in the UI opens them.
- **Tested on Linux only for the latest changes**: the end-to-end and pseudo-terminal scripts ran on Linux (WSL2). `zypi` last ran on macOS before the final changes to `tui/`. The macOS binary of this release is built by CI (a dry run of the release workflow built it) and nobody has started it. There is no Windows binary. The Landlock layer of the sandbox was not tested: the kernel of the test machine (5.10) has none.
- **Open findings in the Python packages**: the low-risk findings F7-02 to F7-09 of the Phase 6 and Phase 7 audit have no fix yet (small defects in the extension API, and notes for the specs). See `docs/AUDIT/AUDIT-PHASE6-PHASE7-2026-09-30.md`, section 8.

## [0.1.0] - 2026-08-05

Initial public release.

### Added

#### pi-agent-core

- **Core runtime (Phase 1)**: `Agent` with steering/follow-up queues, abort, `subscribe()` event barrier; `agent_loop` with pi-compatible event protocol, parallel/sequential tool execution, `terminate` semantics.
- **LangChain adapter**: `StreamFn` over `astream()` for OpenAI / Anthropic / DeepSeek / any `init_chat_model` provider; mock stream for tests (no API keys needed).
- **Production hardening (Phase 2/2.5)**:
  - Cross-provider message replay (`transform_messages`: tool-call id normalization, thinking downgrade, image stripping).
  - Usage & cost tracking with `CostCalculator`.
  - Thinking/reasoning: provider param mapping, streamed `thinking_delta` events, Anthropic signature replay, DeepSeek-style `reasoning_content`.
  - Stream-level retries with exponential backoff + jitter, `Retry-After` aware.
  - Runaway protection: `max_turns` / `tool_timeout`.
  - Guardrail hooks: `before_llm_call` (with `ContextBudget`), `after_llm_call`, `on_agent_end`.
  - Observability: `on_payload` / `on_response` hooks; `run_id` / `turn_id` on every event.
  - Granular stream events: `text_start/end`, `thinking_start/end`, `toolcall_start/end`.
  - Structured output: `response_schema` (Pydantic model or JSON schema).
  - Tool-result images: Anthropic native blocks, user-message fallback elsewhere.
  - OpenAI-compatible gateways via `Model.base_url`.
- **Tool ecosystem (Phase 3.5)**:
  - 7 built-in coding tools: `read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`.
  - Group factories: `create_coding_tools()` / `create_read_only_tools()`.
  - LangChain `BaseTool` → `AgentTool` adapter (`from_langchain_tool`).

#### pi-agent-harness

- **Session tree (H1)**: `SessionRepo` with filesystem storage, `uuid7` IDs, branch/fork semantics, message append/list.
- **AgentHarness runtime (H2)**: orchestration layer over `Agent`, queue rollback, abort aggregation, event-based idle wait.
- **Compaction & tree navigation (H3)**: token-based compaction with branch summaries, `navigate_tree` for branch exploration.
- **Skills, templates & env (H4)**: skill discovery, prompt templates, system prompt injection, `LocalExecutionEnv` for sandboxed execution.
