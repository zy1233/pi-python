## [Unreleased]

### Added

- **An ACP client is asked before a project's own resources are used, and the answer is tied to the files (Phase 7)**: trust used to be a path in `agent.toml` and nothing else, so a project that shipped extensions, `.pi/SYSTEM.md`, `.pi/APPEND_SYSTEM.md` or project-relative skills was quietly ignored until the user edited a file by hand, and once listed it stayed trusted whatever later arrived in the directory (a `git pull` could add an extension that then ran). Now, when a project ships any of those and nothing the project cannot write has decided already (`trusted_projects`, `default_project_trust = "always"` or the older `trust_project_extensions`, `--trust-project-extensions` / `PI_TRUST_PROJECT_EXTENSIONS`), the ACP agent asks. It first says, in an ordinary agent message, which directory and files are involved and what each does (the TUI shows a permission request's title and options only, not its `content`; the names in the message are the repository's to choose, so control characters are written as escapes and names sit in code spans, and a message that cannot be delivered means nothing is asked), then sends `session/request_permission` with `Don't trust` (`reject_once`, listed first) and `Trust and remember` (`allow_always`). There is deliberately no `allow_once` option: clients may answer tool permissions for the user (ACP allows it; the TUI's YOLO mode picks the first `allow_once`), and whether to run a repository's code is not that decision, so with no such option the question reaches a person. Only the exact id of the trust option, selected, is a yes; a cancel, an unknown id or a failing client leaves the project untrusted, and a refusal is not remembered. It asks whatever the `permission` mode is (asking is not trusting). The request goes out after the `session/new` (`load`, `resume`) response, because clients drop requests for sessions they have not registered; until it is answered nothing of the project loads (extensions stay unimported) and the session's first prompt waits (`session/cancel` ends every prompt waiting at that moment, and closing the session ends them too); sessions opened together in one directory are asked one after the other, and a yes answers them all (a refusal is not remembered, so the next one asks again). The answer is saved in `~/.pi-python/agent/trust.json` (version 1; one record per exact directory with a `sha256:` fingerprint of the gated files' contents, the time and what was trusted; written atomically; read fail-closed; a corrupt file is kept as `trust.json.corrupt` instead of being overwritten; delete a project's entry to take the trust back). The fingerprint covers contents, not mtimes (the extensions directory recursively, the two prompt files, the project-relative skills paths; `__pycache__` and `.git` skipped), so a `git pull` that changes one of them asks again and says the files changed since they were trusted; files edited while the dialog is open are not trusted (the disk is checked again after the answer); and if the answer cannot be saved the session is still trusted and the user is told they will be asked again. A project with more than 2000 entries, more than 64 MiB, or unreadable files cannot be fingerprinted, so it is not asked about: list it under `trusted_projects`. New setting `[extensions] default_project_trust = "ask" | "never" | "always"` (upstream pi's `defaultProjectTrust`; default `ask`): `never` neither asks nor trusts (an allow-list entry, the command line or a saved answer still do); `always` trusts every project; the older `trust_project_extensions = true` means `always` unless `default_project_trust` is set. Headless (`-p`) runs never ask, as in upstream's non-interactive modes, but honour a saved answer whose files still match, and their "skipped" notice now says why (not decided, changed since trusted, `never`, too many files). **Behaviour change**: an ACP session in a project that ships such files used to skip them without a word and now asks; set `default_project_trust = "never"` to keep the old behaviour. **Not covered**: a client may auto-approve the request (nothing in ACP prevents that, and the TUI pre-highlights the kind of answer the user confirmed last, so after an "always" answer `Trust and remember` is the highlighted row); files changed after the session started are not re-checked; there is no `/trust` command. New modules `trust_store`, `trust_fingerprint`, `trust_prompt` and `extension_trust.decide_project_trust` / `ProjectTrust` in `pi_agent_cli`; `AgentHarness.set_trust_project_extensions(bool)` (valid until extensions load); `pi_agent_core.extensions.loader.extension_module_names`. Design: Phase 7 spec, section 4.4.
- **Workflow scripts run in a process of their own, under limits the operating system enforces (Phase 7)**: scripts were `exec`'d inside the host's interpreter with a narrowed `__builtins__`, which the audit showed two ways out of (`agent.__globals__['__builtins__']['__import__']`, and `().__class__.__base__.__subclasses__()` to `catch_warnings.__init__.__globals__`); once out, a script had the host's environment (API keys), files, network and event loop, and a `while True` in one froze the host's loop for good, with no way to cancel it. Now every `WorkflowRuntime.execute()` starts one child process (`python -I -S -B -X utf8 sandbox/child.py`: standard library only, nothing of the host importable) with an empty environment (Windows keeps `SYSTEMROOT`, `SYSTEMDRIVE`, `WINDIR`), an empty scratch directory that is removed afterwards, and file descriptors 0 and 1 pointed at the null device, so nothing a script prints can reach the protocol. The script computes there; everything with an effect (sub-agents, the journal, logs, the budget) is requested over a pipe (one JSON object per line, protocol v1) and done by the host, which treats the other end as hostile: a line over `max_message_bytes`, invalid or too deeply nested JSON, an unknown message, a field of the wrong type, a call id that is still in use or a message out of line ends the run (`SandboxProtocolError`) and kills the process; calls in flight, log lines and characters, and phase titles are capped (when calls pile up the host stops reading instead of refusing). Beneath the audit hook the kernel limits the process: on POSIX `RLIMIT_CORE`, `AS`, `CPU`, `NOFILE` and `FSIZE` (soft = hard, so a script cannot raise them); on Linux also `PR_SET_NO_NEW_PRIVS` and `RLIMIT_NPROC=0` (no `fork`, no new threads; not enforced for root); on Windows a Job Object (process memory and CPU time, one process, no UI access, killed when the host lets go of it) and a lowered integrity level (the script can no longer write where the user can, read the host's memory or take its handles). `SandboxLimits.wall_seconds` (off by default) kills the process at a deadline; a host that dies leaves no script process behind. A script that raises makes `execute()` raise `WorkflowScriptError` (a `RuntimeError` whose `str()` is the script's own message, with `error_type` and `line`); a script that is stopped, or cannot be run, raises a `SandboxError` (`SandboxLimitExceeded`, `SandboxCrashed`, `SandboxProtocolError`, `SandboxUnavailable`; also `RuntimeError`s). `WorkflowRuntime(sandbox_limits=SandboxLimits(...))` sets the limits. **What this is not**: the audit hook (it refuses `open`, `os.*`, `socket.*`, `subprocess.*`, `ctypes.*` and the first import of a few modules) is Python, so a script written to get out can undo it, and what the kernel then still allows is listed per platform in the design doc: on Linux it can read any file the user can read (including `/proc/<pid>/environ` of the host and of the user's other processes), truncate or delete files (but not write content) and use the network; on Windows it can read files and use the network (but not write, start a process or read the host's memory). Run the agent in a container if scripts cannot be trusted. **Behaviour changes**: values cross the process boundary as JSON (`args`, `result()`, what `agent()` returns; other objects become strings); `budget` in a script is a read-only view (`add` is gone, the books are the host's); each run costs a process start (about 0.06 s on Linux, 0.14 s on Windows); on Windows the default event loop is required (the selector loop cannot start processes: `SandboxUnavailable`). A call to `agent()` now carries the phase the script was in when it made it: the host answers calls as tasks of its own, by which time a parallel thunk may have moved the script on. Design: `docs/specs/2026-10-01-workflow-sandbox-design.md`.
- **DeepSeek thinking works together with tools on DeepSeek's own API (Phase 6)**: with thinking on, DeepSeek answers 400 to a request that carries tools unless the earlier assistant messages bring their `reasoning_content` back (all of them, turns without a tool call included). The adapter recorded it as a `thinking` block, but `ChatDeepSeek` (checked with 1.1.0) leaves the field out of the request, so thinking plus tools failed after the first tool round. `convert_to_langchain` now keeps a DeepSeek turn's thinking in `AIMessage.additional_kwargs["reasoning_content"]`, and `resolve_chat_model` builds a `ChatDeepSeek` subclass (`adapters/deepseek_replay.py`) that writes it onto every assistant message of the request: an empty string where there is none, as pi's own provider does, and `content: ""` instead of `null` on a tool-call message, as DeepSeek's own samples send it. Only DeepSeek's own API, and only while thinking is asked for (`Model.reasoning=True`, `thinking_level` not `off`); gateways serving DeepSeek models are left alone. Not verified against the real API (no key): the provider matrix's `deepseek` row has a new `thinking_tools` case for that. Spec: Phase 6 §5.5.
- **`[model] reasoning` in `agent.toml` (Phase 6)**: whether the configured model can reason (`Model.reasoning`). Unset, any `thinking_level` other than `off` says it can. See the `Changed` entry on `thinking_level`.
- **Tools can declare what they do: `ToolAnnotations` (Phase 7)**: `pi_agent_core.types.ToolAnnotations` carries the Model Context Protocol's four hints (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`; all optional, and a tool that declares nothing claims nothing). `SimpleTool`, `CodingTool` and `ToolDefinition` (extensions) take `annotations=`; `from_langchain_tool` reads the four hints from `tool.metadata`, where `langchain-mcp-adapters` puts an MCP tool's annotations (a value that is not a real boolean is ignored); `AgentTool` documents the optional attribute. `AgentHarness.check_tool_call` — the one path that both the session's own loop and `workflow` sub-agents go through — looks the tool up by name in the session's tool table and hands its annotations to `tool_call` hooks as `ToolCallEvent.annotations` (a copy, so a hook cannot change the tool's own; `None` when the session has no tool of that name or the tool declares nothing). The agent loop itself ignores them. Built in: `read`, `grep`, `find` and `ls` declare `readOnlyHint`; `web_search` and `fetch_url` declare `readOnlyHint` and `openWorldHint`; `goal_update` and `goal_complete` declare themselves neither read-only nor destructive nor open-world (they only keep notes in the session); `bash`, `edit`, `write` and `workflow` declare nothing, on purpose. The hints are the tool author's word and are not verified. What the CLI does with them: see the `Changed` entry on `ask` mode. Design: Phase 7 spec, section 12 ("Permission model").

### Fixed

- **`PiAcpAgent(home=...)` and `run_print(home=...)` looked for extensions in the default home (Phase 7)**: both resolved their own home for config and sessions but did not pass it to `create_session_harness`, so the user's `<home>/extensions` was read from `~/.pi-python` (or `$PI_HOME`) instead. They now hand it on, which also puts the trust store next to the config it belongs to.
- **`<git_status>` on non-UTF-8 locales (Phase 6)**: git output was decoded with the locale codec (cp936 on Chinese Windows), so a branch such as `功` crashed the snapshot (`AttributeError` from a failed reader thread, failing the turn) and others such as `功能` were rendered as mojibake. Git now runs with `encoding="utf-8", errors="replace"` and `core.quotePath=false` (non-ASCII paths appear verbatim instead of as `"\344\270\255..."` escapes), and any failure omits the section instead of failing the turn.
- **`<git_status>` missing in a fresh repository (Phase 6)**: with no commit yet (`git init`), `git rev-parse --abbrev-ref HEAD` fails, so the section was dropped for every new project. The snapshot now falls back to `git symbolic-ref --short -q HEAD` and shows `Branch: main (no commits yet)`; if even that fails, the section is still omitted.
- **`<git_status>` blocked the event loop (Phase 6)**: the system-prompt callback ran up to three synchronous `git` subprocesses on the event loop, each with its own `timeout_seconds`, so a slow filesystem froze the whole agent process (ACP cancellation, permission replies, other sessions) for up to 3 x `timeout_seconds`. The prompt inputs are now built in a worker thread, and `[git] timeout_seconds` is one budget for the whole snapshot (up to four commands): each command gets what is left, and none is started once it is spent.
- **`tool_call` hooks can no longer overturn a denial**: `AgentHarness` used a last-non-`None`-wins rule, so an extension registered after the permission layer could un-deny a call by returning `{}` or `{"block": False}`. Dispatch now stops at the first blocking verdict, like upstream pi's `emitToolCall`.
- **Extension tools in the system prompt**: `prompt_snippet` / `prompt_guidelines` of extension-registered tools (`workflow` gating guideline, `goal_update`, `web_search`, ...) were never rendered by the CLI; the tools reached the LLM but were missing from the prompt's tool list and guidelines. Because `pi-goal-x` registers its tools in every session, its guidelines were reworded so they hold when no goal is active (they no longer state "You are in goal-driven mode"; the tools apply only after `/goal`).
- **Extensions scanned twice from the home directory**: with the working directory set to the home directory, `~/.pi-python/extensions` was both the user directory and the "project" one and was imported twice. It is now scanned once.
- **Sub-agent model routing and credentials (`pi-dynamic-workflows`)**: a `tier` resolved to an Anthropic model whatever the parent ran on, and the single configured API key was handed to every provider, so a DeepSeek session sent its key to Anthropic. A model override on the parent's own provider also lost the parent's `base_url`.
- **`workflow` sub-agents ran `bash` / `edit` / `write` without asking (`pi-dynamic-workflows`)**: the permission layer is a `tool_call` hook on the session's harness, but every sub-agent got a fresh harness without it, so in `ask` mode a workflow script could write files and run shell commands with no prompt (the `workflow` tool itself was not gated either). Now `workflow` is a permission-gated tool, and every sub-agent tool call goes through the parent session's `tool_call` chain (`AgentHarness.check_tool_call`, exposed to extensions as `HarnessBridge.tool_call_gate`; fail-closed). Calls carry the id `subagent-<hex>:<model>` and `ToolCallEvent.origin = {"kind": "subagent", "cwd": ...}`, so the prompt says the call comes from a workflow sub-agent and where it runs. Permission prompts are serialized per session, so parallel sub-agents cannot stack dialogs. The workflow runtime was a restricted namespace, not a sandbox, and its docs no longer said so. Script-chosen sub-agent `cwd` was shown but not restricted, and `auto` / `always-approve` modes still let sub-agents do what the session may. (The first two were taken care of afterwards: see the sandbox entry under Added and the `cwd` entry under Changed.)

- **Two extensions defined in one module replaced each other (Phase 7)**: an extension's name was `activate.__module__`, so the second of two extensions in one module silently displaced the first (its tools, commands and hooks were gone, with no log line). A module-level `activate` (entry points, scanned directories) is still named after its module; any other callable is now `module.qualname`. Loading under a name that is taken still replaces (reloads and project-overrides-user rely on it) and now logs a warning when the replacement is a different callable. `AgentHarness.load_extension(activate, *, name=None)` takes an explicit name.
- **A failing extension vanished without a trace the user could see (Phase 7)**: `load_all` swallowed every error, a directory module or entry point that raised as it was imported was only a log line, and an ACP client never shows the agent's stderr, so a missing dependency just made the extension seem not to exist. Failures — import errors, an entry point that resolves to nothing, an `activate()` that raises (rolled back as before) — are now recorded in `ExtensionLoader.failed` / `AgentHarness.failed_extensions` (`FailedExtension(name, source, error)`), and the CLI reports them: an ACP agent message after `session/new` and headless stderr, one line per extension with the error cut to its first line. The other extensions still load.
- **An invalid tool name broke every later request (Phase 7)**: `register_tool` accepted any name, but model providers accept only `[a-zA-Z0-9_-]{1,128}` and reject the whole request otherwise, so one extension with a dotted or non-ASCII tool name made the session unusable. It is now refused at registration (naming the extension and the rule) and that extension is rolled back like any other failure.
- **`PI_HOME` was honoured by the CLI only (Phase 7)**: the extension loader and the workflow extension used `Path.home() / ".pi-python"` directly, so with `PI_HOME` set a session read its config from one directory and its extensions, saved workflows and workflow journals from another. One resolver (`pi_agent_core.home.pi_home`: argument, then `$PI_HOME`, then `~/.pi-python`) now serves the CLI, `ExtensionLoader(home=)`, `AgentHarness(home=)`, `ExtensionAPI.home` (`pi.home`), `WorkflowStore(pi_home=)` and `create_workflow_tool(home=)`.
- **`workflow` ran against canned answers when sub-agents could not be built (`pi-dynamic-workflows`)**: without a harness, a model/stream function, or when construction raised, the extension quietly fell back to `MockSubagentExecutor`, so a script "completed" with fake results. It now registers `UnavailableSubagentExecutor(reason)`: the tool (built-in names and background requests too) answers "The workflow tool cannot run in this session: sub-agents are unavailable (<reason>)." and the reason is logged as a warning. The mock remains the test double of `create_workflow_tool()` called with no executor.
- **Workflow run ids and saved-workflow names accepted a trailing newline; a saved script with a non-dict `meta` broke the directory scan (`pi-dynamic-workflows`)**: the patterns ended in `$`, which matches before a final newline, and both values become file names; they are now matched with `fullmatch`. `meta = 5` or `meta = {"name": 5}` in one saved script no longer raises out of the whole scan.
- **`resume_from_run_id` replayed nothing after a parallel run, and recorded failures as answers (`pi-dynamic-workflows`)**: the journal matched calls by position and dropped the rest of the file at the first mismatch, but `parallel()` records in completion order, so a resumed parallel run got no hit at all and one changed step deleted every later answer from disk. A failed `agent()` was also written as a successful `None` and replayed as such. The journal is now a request-keyed cache: a call gets the earliest recorded answer to the same request that this run has not used yet, whatever order it was recorded in; a miss changes nothing on disk; a failure is not recorded, so a resume retries it. Steps whose request is unchanged replay even when an earlier step had to run again, so what a replayed step did to the workspace (files it edited) is not redone.
- **Cancelling a foreground `workflow` did not stop it (`pi-dynamic-workflows`)**: the tool never looked at the abort signal, so after a cancel the run went on to the end (every remaining sub-agent kept spending tokens and editing files) and the tool returned only then. The run is now raced against the signal: on abort it is cancelled and given up to 10 s to unwind (then abandoned with a warning), its worktrees are removed, and the tool answers "cancelled" with the `run_id` and how to resume (finished agents are journaled). A signal that is already aborted starts nothing. `parallel()` / `pipeline()` no longer leave orphan tasks behind when they are cancelled or one branch raises. Background runs are deliberately not tied to the turn that launched them.
- **Sub-agent worktrees lost new files, corrupted non-UTF-8 files and leaked (`pi-dynamic-workflows`)**: `collect_diff` used `git diff HEAD`, which leaves out untracked files, so a file a sub-agent created never reached the project; the patch was decoded with `errors="replace"` and encoded again, so an edit to a GBK file failed with `patch does not apply`; the snapshot lacked `--binary`, so one changed binary file cost the worktree its whole snapshot; and a worktree leaked when its sub-agent failed early, timed out, was cancelled or ran in a background run. The patch is now `git add -A` + `git diff --binary --cached HEAD`, kept as bytes end to end; each call removes its worktree in a `finally`; a foreground run calls `cleanup_all()` in a `finally` and a background run cleans up when it ends.
- **Closing a session left its work running, and a background workflow's result woke the dead session (Phase 7)**: `AgentHarness.close()` only ran the extensions' cleanup callbacks. A turn in flight kept running, the workflow extension's callback waited up to 30 s for background runs to finish, and when one did, its result started a new LLM turn on the closed session; `pi/session/delete` did not call `close()` at all. `close()` now aborts the turn in flight, runs every cleanup callback (a failing one no longer stops the others) and stops the turns the harness started for extensions (`CLOSE_GRACE_S`, 5 s, then cancelled); afterwards `prompt()` raises `AgentHarnessError("invalid_state")` and extensions cannot start turns. `WorkflowManager.close()` cancels background runs and waits for them to unwind (abandoning a run that will not stop after 5 s, with a warning); nothing is delivered after it. ACP `session/close` and `pi/session/delete` both go through `close()`.
- **A background workflow's output entered the conversation as if the user had typed it (Phase 7)**: the result of a background run (text produced by sub-agents that may have read untrusted files or web pages) was injected with `trigger_prompt`, i.e. as a user message, and would have run as a slash command had it started with `/`. It is now delivered with the new `HarnessBridge.trigger_message(custom_type, text, *, details=None)` as a typed `workflow-result` custom message (never slash-dispatched, carrying `runId` / `name` / `status` in `details`), and the output sits inside a `<workflow-output boundary=...>` envelope whose random boundary the output cannot contain, after a statement that it is untrusted data, not instructions. A result that finds a turn already running joins it instead of being dropped. Custom messages are still user-role at the LLM level, so the envelope is a convention the model may or may not honour, not isolation.
- **`fetch_url` fetched anything it was pointed at, without limits, and failed on any large page (`pi-web-access`, Phase 7)**: the URL is chosen by the model, which may have read it on a page someone else wrote, yet the tool followed redirects blindly to any address (the cloud metadata service, `http://localhost:8080/`, or a redirect from a public page to either), read the whole response into memory, and stripped HTML with regexes that are quadratic on malformed markup (2.5 s for 8000 `<script>` tags, 10 s for 16000) on the event loop. It also crashed on its own truncation notice (`TruncationResult` has no `outputLines`), so a page over 2000 lines or 50 KB came back as `Failed to fetch ...` instead of its first 50 KB. Now only `http(s)` URLs on the public internet are fetched: loopback, private, link-local, carrier-grade-NAT, multicast and reserved addresses are refused however they are spelled (`127.1`, `2130706433`, `[::ffff:7f00:1]`, 6to4 and NAT64 forms), and so are `localhost`, `*.local`, `*.internal`, single-label names, URLs with credentials, and any redirect target that fails the same checks (redirects are followed by hand, at most 5). Without a proxy the name is resolved once, every answer must be public, and the request goes to the checked address with the name in `Host` and in the TLS server name: there is no second lookup for a hostile DNS server to answer differently, and certificates are still verified against the name. Through a proxy (`HTTP(S)_PROXY`, `ALL_PROXY`, the Windows system proxy; unchanged) the proxy resolves names, so only literal addresses and the local names above can be refused: a public name that the proxy resolves to a private address is not caught. The body is read with `client.stream()` and cut at 5 MiB, the whole call (redirects and conversion included) takes at most 30 s, and HTML is converted by a linear scanner in a worker thread (the standard library's `HTMLParser` is not linear on malformed input either). A truncated result now says why, and a first line over 50 KB (minified JSON) shows its first 50 KB instead of nothing. The tool does not react to the turn's abort signal; the time limit stops it. Details: Phase 7 spec, section 5.3.
- **`pi-goal-x`: a finished goal came back unfinished, a wrong step index invented a step, and an agent that ignored the reminder was reminded without end (Phase 7)**: the goal was saved only on turns that ended with some step still open, so the turn that finished the last step saved nothing and `goal_complete` never saved; after the session was resumed the goal was active again, with its old steps, and the agent was asked to call `goal_complete` once more. It is now saved when it changes (`/goal`, `goal_update`, `goal_complete`; turns that change nothing write nothing), so the last saved state is the current one. `update_step` with an index that names no step (past the end, or negative) appended an `Unnamed step` and reported success; it now raises `ValueError` naming the steps that exist (`There is no step 5: this goal has 2 steps, indexes 0 to 1. Leave step_index out to add a new step.`), which reaches the model as a failed tool call and changes nothing, and a new step without a description is refused the same way. The status listing numbered steps from 1 while `step_index` counts from 0, so a model that read "Step 2" and passed 2 changed the wrong step, or none; it now lists `[0]`, `[1]`, and so on. The reminder to call `goal_complete` (a message, which starts another turn) was sent on every turn while all steps were done, so a model that ignored it was reminded until the turn limit, which is off by default. It is now sent at most twice (`MAX_COMPLETION_REMINDERS`); the count starts again when a step is reopened or a new goal begins, not when a done step is merely touched.
- **`thinking_level` did nothing on DeepSeek's own API, which thinks by default (Phase 6)**: `_apply_reasoning_params` handled OpenAI and Anthropic only, so for `provider="deepseek"` nothing was sent and the API's default decided. Since DeepSeek V4 that default is thinking on, and DeepSeek's documentation says a request that carries tools must then send `reasoning_content` back on the earlier assistant messages or the API answers 400 — which `ChatDeepSeek` does not do (checked with `langchain-deepseek` 1.1.0 and 1.1.1). The adapter now sends the switch explicitly, in the form DeepSeek documents: `thinking: {"type": "enabled" | "disabled"}` through `extra_body`, and `reasoning_effort` (`minimal` to `high` become `high`, `xhigh` becomes `max`: DeepSeek's own mapping for pi). Thinking is asked for only when `Model.reasoning=True` and `thinking_level` is not `off`; every other case sends `disabled`. This applies when `Model.base_url` is unset (or `DEEPSEEK_API_BASE` points at DeepSeek) or is on `deepseek.com`; gateways that serve DeepSeek models (SiliconFlow, vLLM) get nothing new. Thinking together with tools needs more (the earlier `reasoning_content` has to be sent back) and the CLI has to say whether the model reasons: both are covered by the entries under Added and Changed. None of this was run against the live API (no key was available).
- **Provider matrix: the DeepSeek row asked a non-thinking model for thinking, live tests ran under a plain `pytest`, and the matrix ran only by hand (Phase 6)**: the `deepseek` row used `deepseek-chat` — the non-thinking alias, which DeepSeek retired on 2026-07-24 — with `require_thinking=True`; it now uses `deepseek-v4-flash` (`MATRIX_DEEPSEEK_MODEL` still overrides). `real_llm` was documented as "deselected by default", but nothing did that: the tests only skipped when their key was unset, so a shell with `OPENAI_API_KEY` or `ANTHROPIC_API_KEY` exported turned a plain `pytest` into paid API calls. `pyproject.toml` now sets `addopts = "-m 'not real_llm'"`; `pytest -m real_llm ...` still selects them (the last `-m` wins). The marker moved from the whole matrix module to the live test, so the offline checks of the table and the workflow run by default. The `provider-matrix` workflow, previously manual only, also runs weekly (Mondays 03:00 UTC); a row whose secret is not set skips, so the run stays green.
- **A prompt sent while a `workflow` result was being worked on failed with `busy` (Phase 7)**: the result of a background `workflow` starts an LLM turn of its own (`HarnessBridge.trigger_message`) that has no `session/prompt` behind it, so the client has no way to know the session is occupied, and a prompt it sent meanwhile was refused (`invalid_params`, reason `busy`). `session/prompt` now waits for that turn to end and then runs; `session/cancel` or closing the session ends the wait (stop reason `cancelled`), and a second `session/prompt` from the same client while one is in flight (running or waiting) is still `busy`, since the client knows about the first. ACP's `state_update` (idle / running), which the v2 draft offers for this, is deliberately not sent: it exists only in protocol v2 (an unstable and breaking draft, in which `session/prompt` returns on acceptance and the end of a turn is reported by an idle `state_update`), neither the Python SDK nor the Rust crate under the TUI can read it (the crate's `SessionUpdate` has no such variant and no catch-all, so a protocol 1 client would reject the notification), and this agent answers `initialize` with protocol 1 whatever version is asked for. `test_state_update_is_not_a_session_update_the_sdk_can_read` fails once the SDK learns it, as a prompt to look again. Not verified: how the TUI renders updates that arrive between prompts. Spec: Phase 7, section 13.

### Changed

- **`agent(..., cwd=)` is limited to the project (Phase 7)**: a workflow script could point a sub-agent at any directory; the permission prompt showed it, nothing stopped it. The directory must now be inside the project (`WorkflowRuntime.cwd`): a relative path is read against the project, not the process's current directory; symbolic links and Windows junctions are followed before the comparison; a path outside is a `ValueError` the script can catch, a non-string a `TypeError`, and a NUL character a `ValueError`. The check comes before an agent slot is taken and before the journal is consulted (a resume cannot get around a policy that is tighter than the first run's), the journal hash still holds the `cwd` the script gave, and `HarnessSubagentExecutor` checks again before it creates a worktree, so a caller that uses the executor on its own is covered too. **Migration**: a script that used `cwd` to leave the project has to be rewritten. A worktree-isolated sub-agent (`isolation=True`) still runs at the worktree's root, whatever subdirectory was asked for. Design: `docs/specs/2026-10-01-workflow-sandbox-design.md`, section 8.1.
- **Bridge and lifecycle API (Phase 7)**: `HarnessBridge` gains `trigger_message`; it is a runtime-checkable protocol, so a custom bridge (a test double, say) must add the method to keep passing `isinstance` checks. `AgentHarness` gains `closed`; `close()` is idempotent. `WorkflowManager` gains `close(timeout=5)`, which the extension registers instead of `shutdown()` (still there, no longer used at session end), and `start_background()` raises `RuntimeError` once it is closed. `Journal.truncate_from` is removed and `Journal.try_replay` no longer changes the journal on a miss; `WorktreeManager.collect_diff()` returns `bytes` (it returned `str`).
- **Extension packages declare what they use (Phase 7)**: `pi-web-access-py`, `pi-goal-x-py` and `pi-dynamic-workflows-py` required `pi-agent-core-lc>=0.3.0`, which has no `pi_agent_core.extensions`; the floor is now the core version they ship with (`>=0.4.0`), and `pi-dynamic-workflows-py` also declares `pi-agent-harness-lc` (its sub-agents import `pi_agent_harness`; a plain `pip install` used to leave the workflow tool unable to run). `pi_agent_core/tests/test_extension_packaging.py` checks that every workspace distribution an extension imports is declared, that the floor equals the checkout's version, and that `[tool.uv.sources]` points at the workspace. **Release note**: bumping the core version now fails that test until the three extension floors are raised with it, which is intended: this release's extensions use APIs newer than 0.4.0 (`ExtensionAPI.home`, `pi_agent_core.home`, `HarnessBridge.tool_call_gate`, `HarnessBridge.trigger_message`) and must not be installed against an older core.
- `resolve_tier(tier, tiers=None, *, provider=None)`: built-in tier defaults are now per parent provider (`DEFAULT_MODEL_TIERS_BY_PROVIDER`, currently `anthropic` only; `DEFAULT_MODEL_TIERS` is removed). With any other parent provider a `tier` inherits the parent model. An explicit `tiers` mapping still wins and may name any provider.
- `make_get_api_key(config)` returns the key only for `config.provider`; other providers get `None`, so their SDK reads its own standard variable (for example `ANTHROPIC_API_KEY`). Export that variable when a workflow routes sub-agents to another provider.
- Sub-agent models keep the parent's `base_url` only when they stay on the parent's provider.
- **Project trust also covers prompt files and skills (Phase 7)**: like upstream pi, a project's `.pi/SYSTEM.md`, `.pi/APPEND_SYSTEM.md` and project-relative `[skills].paths` entries (such as `.pi/skills`) are ignored unless the project is trusted by the same rules as extensions (below). They run nothing, but they decide what the model is told, so a cloned repository could rewrite the system prompt just by being opened. An untrusted project falls back to the user's own `~/.pi-python/agent/SYSTEM.md` / `APPEND_SYSTEM.md`. Not gated: `AGENTS.md` / `CLAUDE.md` (upstream loads them whatever the trust), prompts set in `agent.toml`, and absolute or `~` skills paths. The notice to the user lists these files too. **Migration**: a project relying on its own `.pi/SYSTEM.md` or `.pi/skills` must be trusted (answer the question in an ACP client, or allow-list it). New helpers: `config.is_project_relative_path`, `extension_trust.skipped_project_resources`; `skipped_extensions_notice` became `untrusted_project_notice(extensions=, resources=, ...)`.
- **Project-local extensions are opt-in (Phase 7)**: `<project>/.pi-python/extensions` was imported — that is, executed — when any session opened, so opening an untrusted repository ran its code before the first prompt, outside the permission layer. It is now skipped unless the project is trusted, in the spirit of upstream pi's project trust (an ACP client is asked, see Added; there is no `/trust`). Trust comes only from places the project cannot write: `[extensions] trusted_projects = ["/abs/path", ...]` (subdirectories count; relative entries are ignored; symlinks are resolved) or `trust_project_extensions = true` in `~/.pi-python/agent.toml`, `PI_TRUST_PROJECT_EXTENSIONS=1`, or `--trust-project-extensions` (ACP and headless). Skipped extensions are never imported; they are logged and reported to the user (ACP agent message after `session/new`, headless stderr) with how to enable them. Installed entry-point packages, `~/.pi-python/extensions`, and `extensions=` / `extension_dirs=` are unaffected. Library API: `AgentHarness(trust_project_extensions=False)`, `ExtensionLoader.load_all(trust_project_extensions=False)`, `ExtensionLoader.skipped` / `AgentHarness.skipped_extensions` (`SkippedExtensions`). **Migration**: a project that ships its own extensions is asked about in an ACP client (and the answer is bound to the files' content, see Added); elsewhere it must be allow-listed, or answered in an ACP session first (see the Phase 7 spec, §4.4).
- **`<git_status>` privacy note (Phase 6)**: the block (branch name plus the paths of changed and untracked files) is part of the system prompt and therefore goes to the model provider with every request. The README, `agent.example.toml` and the Phase 6 spec now say so and how to disable it (`[git] enabled = false`, `--no-git-context`). The default stays on.
- **`<git_status>` is labelled as a session-start snapshot (Phase 6)**: the 0.4.0 note "on every turn" was inaccurate. Since `bee053c` the harness caches the system prompt for the whole session (a stable prefix for the provider's prompt cache), so the block never tracked the working tree while the model was told nothing about it. The block now opens with "Snapshot taken at the start of this session; it is not refreshed as files change. Run `git status` for the current state." (no timestamp, so the prompt stays byte-stable). Refresh-per-turn was rejected: every file edit would invalidate the cache for the skills section and the whole history after it.
- **`fetch_url` refuses non-public addresses and has no opt-out (Phase 7)**: a URL that names this machine or a private network (`localhost`, `127.0.0.1`, `192.168.x.x`, `*.local`, `*.internal`, a name that resolves to one) now returns `Refusing to fetch ...: ...` without a request, where it used to be fetched. The tool description says so. **Migration**: to read a service on the same machine or the intranet, use a tool the user authorises for it (`bash` with `curl`, say). The redirect limit (5) and the 5 MiB / 30 s bounds are constants in `pi_web_access.fetch_url` (`MAX_REDIRECTS`, `MAX_BODY_BYTES`, `TOTAL_TIMEOUT_S`), not settings.
- **`pi-goal-x` API (Phase 7)**: `GoalState.update_step` raises `ValueError` where it used to append an `Unnamed step`; `create_goal_update_tool` and `create_goal_complete_tool` take an optional keyword-only `on_change` callback, called after every change of the state (the extension uses it to save the goal); `GoalState.format_status()` lists steps as `[0] ...` instead of `Step 1: ...`; `GoalState` gains `reminders_sent`, which is not saved. The `turn_end` hook no longer saves the goal.
- **DeepSeek requests always say whether to think, and live tests are off by default (Phase 6)**: on DeepSeek's own API, `thinking_level="off"` (the default) and `Model.reasoning=False` now send `thinking: disabled`, where nothing was sent before and the API's default (thinking on) applied. **Migration**: code that relied on that default to get reasoning blocks must set `Model.reasoning=True` and a `thinking_level`. Requests to gateways (`Model.base_url` on another host) are unchanged, and so are OpenAI and Anthropic. A plain `pytest` no longer collects the `real_llm` tests (`test_real_llm.py`, `test_pelican_real_llm.py`, the matrix); run them with `pytest -m real_llm ...`. Naming one of those files without `-m` now selects nothing.
- **Tests ignore an exported `PI_HOME`**: since `PI_HOME` became the one home for the extension loader too (Phase 7), tests that point `Path.home()` at a temporary directory found the real home instead on any machine that exports it — four failed under a WSL shell that shares the Windows home. A root `conftest.py` now clears `PI_HOME` for every test; a test that needs it sets it itself.
- **`thinking_level` now takes effect through the CLI (Phase 6)**: the CLI built every model with `reasoning=False`, so the level in `agent.toml` was dropped on OpenAI and Anthropic and, on DeepSeek's own API, the model was always told not to think. `Model.reasoning` now follows the configuration: `[model] reasoning = true|false` if set, otherwise `thinking_level != "off"`. A user with `thinking_level` set to anything but `off` gets the thinking they asked for; if the model rejects reasoning parameters (a non-reasoning OpenAI model, say), `reasoning = false` keeps it out. The default (`off`) is unchanged, and workflow sub-agents still do not inherit `reasoning`.
- **`ask` mode asks about every tool call unless the tool declares itself harmless (Phase 7)**: the permission layer used a fixed set of names (`PERMISSION_TOOLS`: `bash`, `edit`, `write`, `workflow`), so any other tool — in particular every tool an extension registers — ran without a question. It now asks by default and lets a call through unasked only when the tool's annotations say `readOnlyHint` is true, or that it neither is destructive (`destructiveHint` false) nor reaches outside the session (`openWorldHint` false); undeclared, other, non-boolean or malformed hints all mean "ask", as MCP's own defaults do. Tool names no longer matter: `PERMISSION_TOOLS` is gone and `needs_permission(mode, annotations)` replaces `needs_permission(mode, tool_name)`. `auto` and `always-approve` are unchanged. **Behaviour change**: in `ask` mode an extension tool that declares nothing now interrupts the user where it used to run silently, and a `workflow` sub-agent's call is judged by the session's tool of the same name (a name the session lacks is asked about). The tools shipped here declare themselves as listed under Added, so `read`, `grep`, `find`, `ls`, `web_search`, `fetch_url` and the `goal_*` tools still run without a question, while `bash`, `edit`, `write` and `workflow` ask. **Migration**: an extension whose tool only reads, or only keeps the agent's own notes, should pass `annotations=`; `agent.toml` has no per-tool allow-list, so a third-party tool that declares nothing can be let through only by `permission = "auto"`. **Not covered**: the hints are not verified, and the CLI does not connect MCP servers (`mcpServers` in `session/new` is ignored), so their hints are not read either. The MCP specification says a client must treat annotations as untrusted unless they come from a server it trusts (a hostile server can label a destructive tool read-only); `from_langchain_tool` passes `tool.metadata`'s hints on as they are, so a caller who connects MCP servers it does not trust has to remove them first. Design: Phase 7 spec, section 12.
